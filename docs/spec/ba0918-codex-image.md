# ba0918-codex-image 仕様

## 目的

ゲームや Web サイトで使う画像素材を、テイストのブレを抑えて作れるようにする。

画像生成のモデルは、見た目の品質が高い。一方で、サイズ、比率、ドットのマス目のような数値の
仕様は、プロンプトで頼んでも守られない。同じ注文を繰り返したときにテイストが揃う保証もない。
そこで、このスキルは生成を Codex CLI の画像生成に任せ、テイストの手がかり（参照画像と
スタイル定義）の管理、プロンプトの組み立て、決まった手順の後処理、自動の検収を受け持つ。

一文でいえば: ユーザーのざっくりした指示を、[シリーズ](../../PROJECT.md#ba0918-codex-image)
の定義に沿ったプロンプトに直して `codex exec` で画像を生成し、決まった後処理と自動の検収を
通してから、シリーズのフォルダーに残す。

用語（シリーズ、ドット絵、ドット絵風、テンプレート画像）の定義は `PROJECT.md` の Glossary 節にある。

このスキルは Codex 専用である。[ba0918-codex-exec](ba0918-codex-exec.md) と同じく、名前に
codex を入れて、特定のプラットフォームに寄っていることを示す。ただし ba0918-codex-exec には
依存しない。各スキルは単体でインストールされるためである。

### 移植性と単体完結

本文は Codex CLI、Python、Pillow、uv 以外の固有のツール名や API 名に依存しない自然言語で書く。
Codex CLI はこのスキルの扱う対象、Python・Pillow・uv は同梱する後処理を動かす手段であり、
`PROJECT.md` の「特定の CLI だけで通じる呼び出し形式は書かない」の例外として扱う。
他のスキルに依存しない。配布物は英語で書く。

- 成功条件: `agentskills validate ./skills/ba0918-codex-image` が通る。本文に他のスキルへの
  依存、絶対パス、特定の利用者の環境の値がない（C-01）。
- 反例: 「ba0918-codex-exec で実行する」と書かれている。

### 実行してよい条件

動くのは、ユーザーがこのスキルか Codex での画像生成を名指ししたときだけである（例: 「codex-image
でコウモリの立ち絵」「Codex で素材を作って」）。画像の話題が出ただけでは動かない。この条件を
説明文（description）と本文の両方に書く。

- 成功条件: 説明文と本文に名指しの条件が書かれている。画像生成について質問しただけの会話で
  `codex exec` が起動しない（C-02）。
- 反例: 「このページにヒーロー画像がほしいね」という会話で生成を始める。

### 外部への送信

プロンプト、参照画像、テンプレート画像がモデルの提供元（OpenAI）に送られる。プロジェクトの
ファイルは作業フォルダーに置かない。ただし sandbox は書き込みだけを制限し、読み取りは制限しない
ため、Codex が作業フォルダーの外を読まないことまでは保証しない。ユーザーに聞かれたら、そのことを伝える。名指しされた時点で送ってよいと判断済みとみなし、生成の前に改めて確認
しない。送られることを README、説明文、本文の 3 か所に書く。

Codex は素材ごとに作る一時的な作業フォルダーで実行し、そこにはプロンプト、参照画像、テンプレート
画像だけを置く。添付する画像は 1 回の実行で 1 枚で、立ち絵・イラスト・Web 素材では参照画像、アニメーションでは
テンプレート画像（立ち絵を含む）を `-i` で添付する。プロンプトは標準入力で渡す。
Codex の stdout と stderr は作業フォルダーのファイルに書く。sandbox はその作業フォルダーの中だけ
書き込みを許す設定にする。作業フォルダーは git の管理外なので、Codex が git の管理外での実行を
拒まないよう `--skip-git-repo-check` を付ける。モデルは指定せず Codex の既定を使い、
ユーザーが指定したときだけ `--model` を付ける。

- 成功条件: Codex の作業フォルダーにプロジェクトのファイルが含まれない（C-03）。説明文、本文、
  README に送信のことが書かれている（C-01）。
- 反例: プロジェクトのリポジトリの中で `codex exec` を実行する。

### 前提の確認

生成の前に、`codex --version` と `codex features list` を実行する。コマンドが見つからないか、
`image_generation` が有効でなければ、何も生成せずに止めて、足りないものを伝える。後処理を
動かす手段（uv、または Pillow の入った Python）が見つからないときも同じにする。

- 成功条件: `image_generation` を無効にした Codex で頼むと、生成されずに、有効でないことが返る（C-04）。
- 反例: 生成してから後処理で Pillow が無いことに気づき、生成物を捨てる。

### シリーズ

シリーズのフォルダーの置き場所は、ユーザーが指定するプロジェクト内のフォルダーである。中身は
次のとおり。

```
<シリーズのフォルダー>/
  series.md          シリーズの定義
  reference.png      参照画像
  <素材名>/           素材ごとのフォルダー（アニメーションは <キャラ名>-<モーション名>/）
    final.png        完成品（アニメーションならシート）
    raw.png          加工なしの元画像
    prompt.md        使ったプロンプトと、人の指摘の追記
    preview.gif      プレビュー（アニメーションのみ）
```

`series.md` の front matter は後処理と検収が読む契約で、次の 4 項目を持つ。本文には、
参照から引き継ぐもの（絵柄）と引き継がないもの（形、表情など）と、その他のテイストを文章で書く。
ドット絵風はイラストとして扱い、そのことは本文に書く。

| 項目 | 値 | 使う種類 |
|---|---|---|
| `kind` | `pixel`（ドット絵）、`illustration`（イラスト）、`web`（Web 素材） | すべて |
| `canvas_dots` | 正方形のキャンバスの 1 辺のドット数（例 `32`） | `pixel` |
| `size` | 出力の `幅x高さ`（px、例 `1024x1024`） | `illustration`、`web` |
| `transparent` | 背景を透過するか（`true` / `false`）。既定値はなく、使う種類で欠けていれば定義の誤り | `pixel`、`illustration` |

ドット絵の `reference.png` は後処理済みの完成品（例 32×32）で持ち、生成に渡すときだけ
`template` が最近傍法（ぼかさない拡大）で 1 ドット約 10px に拡大する。

- 成功条件: `canvas_dots` の無い `kind: pixel` の `series.md` を読むと、`check` が
  定義の誤りとして、JSON の判定を返さずにエラーで終わる（T-01）。
- 反例: シリーズの定義を素材ごとのフォルダーに分けて持ち、どれが正しいか分からなくなる。

### 新しいシリーズの始め方

参照画像がまだないシリーズでは、スタイルの説明だけで、色味や頭身などの方向を少しずつ変えた
候補を 3 枚作る。候補には画像を添付せず、候補ごとに作業フォルダーを分ける。後処理と検収には、
スタイルの説明から作った一時的な `series.md` をプロジェクトの外に置いて使う。候補にも後処理と
検収をかけ、完成形で見せる。自動の作り直しはせず、不合格の候補には理由を添える。ユーザーが 1 枚選び、その後処理済みの画像を `reference.png` にして、
`series.md` を書く。
2 枚目以降は参照画像を使って 1 枚ずつ作る。複数の候補は、ユーザーが頼んだときだけ作る。

- 成功条件: 新しいシリーズで頼むと後処理済みの候補が 3 枚示され、選んだ 1 枚が `reference.png` に、
  定義が `series.md` に残る（C-05）。
- 反例: 最初の 1 枚をエージェントが選んで参照画像にする。

### ざっくりした指示の清書

ユーザーはざっくり指示し、エージェントがそれをプロンプトに直す。シリーズの定義から補えること
（種類、サイズ、ドットの粗さ、テイスト）は聞かずに補う。補えないもの（どのシリーズか不明、
新しいシリーズの最初のサイズや用途）だけ、生成の前にまとめて聞く。組み立てたプロンプトは、
生成の前に確認をとらずに投げ、`prompt.md` に残す。

参照画像を使うプロンプトでは、引き継ぐものと引き継がないものを分けて書く。分けないと、
目や形まで参照がコピーされるためである。プロンプトには、生成した画像を縮小・切り出し・加工
せずにそのまま保存することを必ず入れる。頼まないと Codex が毎回違う方法で後処理するためである。

素材名は、エージェントが指示から短い英語で決め、生成を始めるときに伝える（例 `bat`、
`bat-attack`、`top-hero`）。ユーザーが指定すればそれを使う。同じ名前のフォルダーがあれば、
上書きの前に作り直しとして上書きしてよいか聞く。

- 成功条件: シリーズが決まっている状態で「コウモリの立ち絵」とだけ頼むと、質問なしで生成が
  始まり、`prompt.md` に引き継ぐもの・引き継がないもの・加工しない保存の指示がある（C-06）。
  既存の素材名と重なると、上書きの前に聞かれる（C-06）。
- 反例: 生成のたびにプロンプトを見せて承認を待つ。既存の素材を黙って上書きする。

### 種類ごとの後処理

後処理は決まった手順で行い、Codex には任せない。

| 種類 | 後処理 |
|---|---|
| ドット絵 | 1 ドットごとのマス目の中心の色を拾う。色数は減らさない。`transparent: true` なら不透明度 128 以上を不透明、未満を透明にする。`false` なら背景ありのまま |
| イラスト（ドット絵風を含む） | `transparent: true` なら `size` に収まるように縮小し、足りない分を透明で埋める。元画像が `size` より小さければ拡大せず、元の大きさのまま中央に置く（拡大するとぼやけるため）。`false` なら `size` の比率で中央から切り出して縮小する。縁の半透明は残す |
| Web 素材 | 常に不透明。`size` の比率で中央から切り出し、`size` に縮小する |

Web 素材のプロンプトには、指定の比率で描くことと、端から約 1 割に主題を置かないことを入れる。

- 成功条件: 1 ドットが 10px の 32×32 の合成画像に半透明の縁を足して `process` すると、元の
  32×32 と一致する（T-02）。16:9 から少しずれた画像が、指定の `size` ちょうどになる（T-03）。
  イラストの縁の半透明が残る（T-04）。
- 反例: ドット絵の色を自動で減らし、目のハイライトが潰れる。

### アニメーション

1 枚のシートに 1 モーションを入れる。コマ数は 2〜16 で、既定は 8 である。列は 4 で固定し、
行数はコマ数を 4 で割って切り上げた数にする（4 コマは 1 行×4 列、8 コマは 2 行×4 列、
12 コマは 3 行×4 列、16 コマは 4 行×4 列）。空いたコマは透明のまま残す。列を固定するのは、
ゲーム側でシートからコマを切り出しやすくするためである。

アニメーションはドット絵の `transparent: true` のシリーズだけが対象である。`transparent: false` の
シリーズで頼まれたら、生成せずに、背景ありのシリーズではアニメーションを作れないと返す。足元を
不透明なドットの一番下で見つけることと、空いたコマを透明に残すことが、背景ありでは成り立たない
ためである。テンプレート画像の左上のコマには、そのキャラクターの
採用済みの立ち絵（`<キャラ名>/final.png`）を置く。立ち絵がないキャラクターの
アニメーションは作らず、先に立ち絵を作るよう返す。

後処理（`process`）では、左上のコマを元の立ち絵で上書きしてから、全コマの足元を左上のコマの
高さに揃える。揃えるとコマの上端から体がはみ出すコマがあれば、完成品を作らずにエラーで終わる
（この状態は [検収と作り直し](#検収と作り直し) で不合格として先に拾う）。ジャンプなど地面を離れるのが正しい
モーションで、指示がそう言っているときは揃えない。左右は揃えない。白フラッシュやフェードの
ような演出のコマは描かないようプロンプトで指示する。ユーザーが明示的に頼んだときだけ描かせる。

プレビューの GIF は既定で 1 コマ 120ms、指示で変えられる。

1 行×4 列や 2 行×4 列の横長のテンプレート画像を渡したときの出力の比率は未確認である。外れた場合は、
[検収と作り直し](#検収と作り直し) の 1 ドットの大きさの検収（縦も見る）で拾う。

- 成功条件: 足元の高さがコマごとに違う合成シートを `process` すると、左上のコマが元の立ち絵に
  なり、足元がそれに揃い、左右の位置は変わらない（T-05）。立ち絵のないキャラクターの攻撃モーションを頼むと、生成されずに
  立ち絵を先に作るよう返る（C-07）。
- 反例: テンプレート画像なしでシートを作らせ、別の形のキャラクターになる。

### 検収と作り直し

`check` は加工なしの元画像を判定するだけで、画像を書き換えない。結果は
`{"result": "pass" | "fail" | "undetermined", "reasons": [...], "measures": {...}}` の JSON で返す。
`measures` は合否に関係なく毎回出す測定値で、`dot_size_x`、`dot_size_y`（ドット絵とアニメーションで
推定した 1 ドットの大きさの px。推定できなければ `null`）と、`top_left_diff`（アニメーションで左上の
コマの違うドットの割合）を持つ。その種類で測らない項目は持たない。

| 種類 | 判定 |
|---|---|
| ドット絵 | 1 ドットの大きさ（推定値）が、横は期待値（画像の幅 ÷（`canvas_dots` × 列数））、縦は期待値（画像の高さ ÷（`canvas_dots` × 行数））の ±10% 以内。推定できないときは `undetermined`。`transparent: true` なら、期待のマス目で拾った各コマ（1 枚の素材はその 1 枚）の四隅のドットが透明 |
| アニメーション | 上に加えて、期待のマス目で拾った左上のコマと元の立ち絵とで違うドットの割合が 5% 以下（推定値を使わないので常に判定できる）。コマ数の範囲のどのコマにも不透明なドットがある（空のコマは番号を理由に書く）。足元を揃えるシートでは、揃えたときにどのコマもコマの上端からはみ出さない |
| イラスト | `transparent: true` なら四隅付近（各隅から辺の 2% 四方）が透明（不透明度 8 未満。255 段階）。`false` なら判定する項目はなく合格 |
| Web 素材 | 元画像の縦横比が `size` の縦横比の ±5% 以内 |

イラストと Web 素材のサイズは後処理が必ず `size` にするため、検収では見ない。Web 素材の縦横比を
見るのは、中央から切り出して削れる幅を元画像の約 5% までに抑え、主題が欠けるのを防ぐためである。

ドットが違うとは、透明か不透明か（不透明度 128 が境目）が違うか、RGB の各成分の差の合計が
60 を超えることをいう。イラストの四隅で不透明度 8 未満を透明とみなすのは、生成ツールが背景に残す目に見えない
かすかなノイズ（不透明度 1 など）で、正しい画像を不合格にしないためである。±10%、5%、128、60、2%、縦横比の ±5%、8 は試行で使った値か仮の値で、使いながら調整する。

不合格なら自動で作り直す。自動の作り直しは 2 回までで、それでも不合格なら、一番ましな結果と
不合格の理由を添えてユーザーに渡す。一番ましな結果は `measures` で比べ、ドット絵なら縦横のうち
期待値からのずれの大きい方が最も小さいもの、アニメーションなら `top_left_diff` が最も小さいもの、
数値で比べられないときは最後に作ったものである。一番ましな結果が後処理で完成品を作れない（上端から
はみ出す）ときは、素材のフォルダーに `raw.png` と `prompt.md` だけを置き、前の版の `final.png` と
`preview.gif` は消して、完成品を作れなかったことと理由を渡す。新しい元画像と古い完成品という
食い違った組み合わせを残さないためで、前の版は git で追える。自動の作り直しは同じプロンプトで行い、前の試行の元画像は
作業フォルダーの外の一時フォルダーに移して、作業フォルダーには次の試行に使うものだけを置く。

判定した項目のどれかが不合格なら全体を `fail` にする。不合格の項目がなく、判定できない項目が
あるときだけ全体を `undetermined` にする。`undetermined` は不合格にせず、そのことを添えて渡す。
作り直しの途中で Codex の終了コードが 0 以外になったとき、または終了コードが 0 でも作業フォルダーに
元画像がないときは、その場で止め、回数に数えず、[実行と後始末](#実行と後始末) のとおり作業
フォルダーを残す。
最後は必ずユーザーが見て判断する。ユーザーが不採用にしたら、指摘をプロンプトに足して
作り直す。この作り直しは自動の回数とは別で、上限はない。前の結果は上書きし、指摘は
`prompt.md` に追記する。

- 成功条件: 期待値ちょうどと ±10% の内側の画像が合格し、外側の画像が不合格になる（T-06）。
  左上のコマの違いが 5% の内側と外側で合否が分かれ、`check` の前後で画像が変わらない（T-07）。
  四隅に不透明なピクセルがあるイラストが不合格になる（T-08）。縦横比が ±5% の内側と外側の Web 素材の
  元画像で合否が分かれる（T-16）。四隅に不透明なドットがある透過のドット絵と、空のコマがあるシートが
  不合格になる（T-17）。`measures` が合否に関係なく出る（T-18）。3 回とも不合格の場合に、自動の作り直しが 2 回で止まる（C-08）。
- 反例: 不合格のまま何も言わずに `final.png` にする。作り直しを上限なく繰り返す。

### 実行と後始末

Codex の実行に時間制限はつけず、終わるまで待つ。終わったら、必要なファイルをシリーズの
フォルダーに移し、作業フォルダーを消す。Codex の終了コードが 0 以外のとき、または終了コードが 0 でも
元画像がないときだけ作業フォルダーを残し、その場所と stderr のファイルの場所を伝える。Codex が自分のホームに残す生成画像には触らない。

- 成功条件: 成功した生成の後に作業フォルダーが残っていない（C-03）。
- 反例: 失敗したときも作業フォルダーを消し、原因を調べられなくなる。

### 後処理の入り口

後処理と検収は `scripts/codex_image.py` 1 本にまとめ、サブコマンド `template`（テンプレート
画像を作る）、`process`（後処理）、`check`（検収）、`preview`（GIF を作る）を持つ。テストは
この入り口から呼ぶ。Python と Pillow で書き、`uv run --with pillow` で動かすことを想定する。

サブコマンドの細かい引数（シートの行数・列数、足元を揃えない指定、`series.md` の場所の渡し方など）
は実装の計画で決める。

- 成功条件: 4 つのサブコマンドが T-01〜T-10 の入力で期待どおりに動く。
- 反例: 後処理の手順をエージェントがその場で書き、毎回違う方法になる。

### テスト

テストはスキルのフォルダーの外の `tests/ba0918-codex-image/` に pytest で置き、合成した画像を
使う。`PROJECT.md` の Test 欄に `uv run --with pytest --with pillow pytest tests/ba0918-codex-image`
を書く。

- 成功条件: `tests/ba0918-codex-image/` がスキルのフォルダーの外にあり、`skills/ba0918-codex-image/`
  にテストのファイルがない（C-01）。
- 反例: テストが `skills/ba0918-codex-image/` の中にあり、配布物に含まれる。

## 保存する状態と寿命

| 状態 | 置き場所 | 寿命 |
|---|---|---|
| シリーズの定義、参照画像、素材 | ユーザーが指定したプロジェクト内のフォルダー | ユーザーが消すまで。作り直しは上書きし、前の版は git で追う |
| 作業フォルダー | 一時ディレクトリ | 成功したら消す。Codex の終了コードが 0 以外か、元画像がなければ残す |
| Codex の生成画像とセッション | Codex のホームディレクトリ | Codex の管理に任せる |

## 外部依存

- Codex CLI（`image_generation` が有効なもの）
- uv、または Pillow の入った Python
- テストのみ: pytest

## 人の判断点

| 場面 | 人が見るもの | 決めること |
|---|---|---|
| 新しいシリーズ | 候補 3 枚 | 参照画像にする 1 枚 |
| 素材ができた | 完成品、プレビュー、検収の結果 | 採用か、指摘して作り直すか |
| 自動の作り直しが尽きた | 一番ましな結果と不合格の理由 | 採用か、指摘して作り直すか |
| 素材名が重なった | 既存の素材名 | 上書きしてよいか |
| Codex が失敗した | 作業フォルダーと stderr の場所 | 調べるか、やり直すか |

## 作らないもの

- 動画、音声
- SVG などのベクター画像
- シリーズに属さない既存画像の編集（写真の加工など）
- 一度に多数を作る一括生成（必要になったら別の仕様で考える）
- ワークフローからの自動の呼び出し
- 横長のドット絵のキャンバス

## 却下した案

- ba0918-codex-exec に依存する: 単体でインストールした環境で壊れるため。
- 生成の手段を抽象化して環境に選ばせる: ユーザーが Codex 専用と決めたため。
- 生成の前に毎回プロンプトを見せて確認する: ざっくり指示で済ませる使い方とぶつかり、数分かかる
  生成のテンポを落とすため。
- モデルを必須の入力にする: ba0918-codex-exec では送信先の提供元を選ばせるために必須にしたが、
  このスキルは Codex の画像生成専用で提供元が決まっているため。
- 後処理を Node.js と sharp で書く: 依存が重く、試行で使われたのは偶然のため。
- Codex の実行に時間制限をつける: 止めるときに Codex 本体まで確実に止める仕組みが要り、自動の
  作り直しの上限で全体の時間は頭打ちになるため。
- 演出のコマを既定で描かせる: 描かれ方が毎回変わり、フェードの半透明は後処理で残らないため。
- 新しいシリーズの候補 3 枚も自動で作り直す: 最大 9 回の生成になり、お金がかかるため。

## 未決

  並べて空きコマを無視する形に切り替えるか（決める人: ユーザー、実際に使ってから）。

## 委任

- `scripts/codex_image.py` のサブコマンドの細かい引数は、実装の計画で決める。サブコマンドの役割と
  `check` の JSON は、この仕様で決まっているため、どの引数の形でも承認した振る舞いは変わらない。

## 自動テスト

- T-01: `canvas_dots` の無い `kind: pixel` の `series.md` と、`transparent` の無い `kind: illustration`
  の `series.md` で、`check` が JSON の判定を返さずにエラーで終わる。
- T-02: 1 ドット 10px の 32×32 の合成画像（縁に半透明あり）を `process` すると元の 32×32 と一致する。
- T-03: 16:9 から少しずれた Web 素材が中央から切り出され、`size` ちょうどになる。
- T-04: イラストの `process` で縁の半透明が残り、`size` ちょうどになる。
- T-05: 足元の高さが違う合成シートの `process` で、左上のコマが元の立ち絵になり、足元がそれに揃い、左右は変わらない。
- T-06: 1 ドットの大きさが期待値ちょうど、±10% の内側、外側の画像で合否が分かれる。横だけ合って縦が外れた画像も不合格になる。
- T-07: 左上のコマの違いが 5% の内側と外側で合否が分かれ、`check` の前後で画像が変わらない。
- T-08: 四隅に不透明なピクセルがあるイラスト（`transparent: true`）が不合格になる。
  `transparent: false` のイラストが中央から切り出されて `size` ちょうどになる。
- T-09: `template` が、4 コマで 1 行×4 列、6 コマで 2 行×4 列、16 コマで 4 行×4 列の、1 ドット約
  10px のテンプレート画像を作り、左上のコマだけに立ち絵を置く。
- T-15: 足元を揃えると上端からはみ出すコマを含むシートで、`check` が理由を添えて不合格を返し、
  `process` が完成品を作らずにエラーで終わる。
- T-16: `size` が 16:9 の Web 素材で、縦横比が ±5% の内側の元画像が合格し、外側の元画像が不合格になる。
- T-17: `transparent: true` のドット絵で四隅のドットが不透明な元画像と、8 コマのうち 3 コマ目が空の
  シートで、`check` が理由を添えて `fail` を返す。
- T-18: 合格・不合格・判定できないのどの結果でも、`check` の JSON に `measures` があり、ドット絵では
  `dot_size_x`・`dot_size_y`、アニメーションではさらに `top_left_diff` を持つ。推定できないときは
  `dot_size_x`・`dot_size_y` が `null` になる。
- T-19: `size` より小さい透過のイラストの元画像を `process` すると、拡大されずに中央に置かれ、周りが
  透明な `size` ちょうどの画像になる。
- T-20: `transparent: true` のイラストで、四隅に不透明度 7 のピクセルだけがある元画像は合格し、不透明度 8 の
  ピクセルがある元画像は不合格になる。
- T-10: `preview` が、シートからコマ数分の GIF を作り、既定で 1 コマ 120ms、指定で変わる。
