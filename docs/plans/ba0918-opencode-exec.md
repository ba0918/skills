# ba0918-opencode-exec 実装計画

## Goal

呼び出し元が用意したプロンプトと環境で `opencode run`（v2）を 1 回実行し、終了コード・出力の
ファイル・変更一覧を返す単体スキル `ba0918-opencode-exec` が、このリポジトリの `skills/` に入り、
README から使い方と注意点が分かる状態にする。

## Specification

`docs/spec/ba0918-opencode-exec.md`（コミット `aa4b464` で承認、出力の置き場所の検査と前置きのコマンドの受け取り方を後続のコミットで補足）。以下、節は `#見出し名` で示す。
この計画は仕様の文章を写さない。各ステップで挙げた節を、必ず仕様書そのもので読むこと。

用語（実行役スキル、前置きのコマンド、変更一覧）の定義は `PROJECT.md` の Glossary 節の
「ba0918-opencode-exec」にある。仕様の本文もこれらの用語をこの意味で使っている。

## Approach and why

成果物はコードではなく、エージェントが読む指示文書（`SKILL.md`）である。書き方の制約は次の 4 つ
で、どれもこの計画の順番と書き方を決めている。

1. **本文は英語で書く。** `PROJECT.md` の「言語方針」による。仕様は日本語なので、実装は翻訳を伴う。
   仕様の日本語の言い回しを決まった文面として埋め込まず、意図を英語で書く。
2. **本文に名前を出してよいコマンドは opencode と git だけにする。** 仕様 `#移植性` による。
   ほかの操作（ファイルの中身を読む、一時ディレクトリを作る、プロセスとその子孫を止める、時間を
   計る、ファイルの中身のハッシュを取るうち git を使わないもの）は、特定のコマンド名を出さずに
   「〜する」と動作で書く。エージェント固有の仕組み（バックグラウンド実行の機能名など）も書かず、
   「セッションが終了を待てる形で実行する」のように書く。サンドボックスの具体的なツール名は、
   本文にも README にも書かない（`#移植性`、`#README`）。
3. **このスキルは副作用のある手順のスキルである。** 実行してよい条件（`#実行してよい条件`）と、
   内容が外部に送られること（`#外部への送信の明示`）を、`description` と本文の両方に書く。
   `description` にはこの 2 つのほかに、何をするスキルかと、ユーザーが実際に言いそうな言葉
   （英語と日本語）を書き、手順の中身は書かない。1024 文字以内に収める。
4. **本文は 1 ファイルに収める。** 実行のたびに全部の手順を通るので、状況によってだけ要る部分がなく、
   `references/` に分ける理由がない。`PROJECT.md` の目安どおり 500 行以内に収める。

変更一覧の作り方（仕様 `#実行前の確認` の手順 2 と `#変更一覧`）は git のコマンドで書ける。
使う git のコマンドの選び方は実装者に任せるが、次を満たすことが条件である。

- 実行前と実行後のそれぞれで、HEAD、変更のあるファイルの一覧、無視されていない未追跡の
  ファイルの一覧、それぞれのファイルの中身のハッシュを取れる。
- HEAD が動いたときは、前後のコミットの間で変わったファイルの一覧を取れる。
- 比べる対象は、実行前に変更のあったファイル、実行後に変更のあるファイル、実行前後の未追跡の
  ファイル、コミットの間で変わったファイルを合わせたものにする。実行前だけ変更があって実行後に
  HEAD と同じ中身に戻ったファイルも、この集め方なら取りこぼさない。

git の管理下でない場合と、git 自体が見つからない場合は、どちらも「変更一覧を検出できない」として
扱う（仕様 `#外部依存` の「無ければ変更一覧を検出できない」）。

実行ごとに書くファイル（stdout、stderr、実行前の記録）は、どれも実行ごとに異なる名前にし、既存の
ファイルを上書きしない（仕様 `#コマンド` と `#出力ファイル`。実行前の記録も同じ置き場所に書くため、
同じ規則を当てはめる）。

## Step order and prerequisites

作業は `ba0918-opencode-exec` ブランチで行う。このブランチがまだなければ、`main` の最新（仕様と
計画のコミットを含む）から作って切り替える。

1 → 2 → 3 → 4 → 5 の順に進める。

- Step 1 で骨組みと `description` を作り、バリデータの通過を先に確かめる。以降のステップはすべて
  この `SKILL.md` に書き足すので、frontmatter の誤りを最後に見つけると全部やり直しになるからである。
- Step 2 の入力と実行前の確認を、Step 3 の結果の組み立てより先に書く。Step 3 の変更一覧は、
  Step 2 で書く「実行前の記録」を前提にしているからである。
- Step 4 の README は、スキルの振る舞いが確定してから書く。
- Step 5 は全体の確認で、最後に行う。

コミットは各ステップで 1 つ作る。規則は次のとおり。

- ファイルは 1 つずつ名前を指定してステージする。`git add -A` や `git add .` は使わない。
- メッセージは日本語で、`<type>: <件名>` の形（Conventional Commits）。件名と本文には、変更の結果と
  理由を書く。「Step 2」のような計画の手順名や、作業の経緯は書かない。
- Step 5 で直すところがなければ、コミットは作らない。

## Stop conditions

次のときは作業を止め、何が起きたかを添えて引き渡す。

- 仕様の意味が決まっていない、または承認済みの内容から外れないと書けない箇所が見つかった。
- 仕様のとおりに書くと、`#移植性` に反して opencode と git 以外のコマンド名を本文に出さざるを
  得ない箇所が見つかった。
- 取り消せない操作・特権の要る操作・危険な対象への操作が必要になった。
- 同じ問題が別の場所にも広がっていると分かった。
- やり方を変えても先に進まない。
