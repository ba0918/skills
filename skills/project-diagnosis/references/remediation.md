# 導入・改善の進め方

診断でユーザーが承認した項目を実際に導入するときの指針。

---

## 共通原則

### 最小構成から始める

そのエコシステムで最も標準的な選択肢を、既定の設定で入れる。
ルールの細かい調整、厳格度の引き上げ、追加プラグインは後回しにする。
初回導入で設定を作り込むと、レビューが困難になり、合わないルールで開発が止まる。

### 導入の順序

依存関係があるので、この順で進める。

1. **シークレット・gitignore** — 事故が進行中の可能性があるため最優先
2. **環境の再現性** — これが無いと他の検査が「手元では動かない」で終わる
3. **フォーマッタ** — 最も摩擦が少なく、以降の差分ノイズを減らす
4. **linter・型チェック**
5. **テスト**
6. **CI** — 上で入れた検査の置き場所。**hook より先**
7. **git hook** — CI にある検査の一部を前倒しするだけのもの
8. **依存の自動更新**

CI より先に hook を入れない。hook は回避できるため、CI が無い状態の hook は強制力を持たない。

### 既存コードの違反をどう扱うか

導入時にほぼ必ず、既存コードが大量に新しいルールに違反する。選択肢は 3 つ。

- **一括修正する** — フォーマッタ向き。ただし**設定追加とは別コミットに分ける**。一括整形のコミットハッシュを blame の無視リストに登録すると、履歴が読める状態を保てる
- **段階導入する** — linter・型チェック向き。既存の違反を抑制した状態から始め、新規コードにのみルールを適用する。多くのツールにベースライン機能がある
- **範囲を絞る** — 新しく書かれる領域や中核モジュールだけを対象にし、徐々に広げる

**やってはいけないこと**: 数百ファイルに及ぶ自動修正を、機能変更と同じコミットに混ぜる。

### 検証してから報告する

導入した検査は必ず実行する。

- 正常なコードで通ること
- 意図的に違反させたコードで落ちること（ゲートとして機能するかの確認。ここまで見ないと「設定しただけ」になる）

確認していないものを「導入した」と報告しない。

### 入口を一本化する

追加した検査は、CI・hook・ドキュメント・開発者の手元から**同じコマンド名**で呼べるようにする。
その言語の慣習に沿った実行方法（スクリプト定義、タスクランナー、Makefile など）に登録し、
CI と hook はそれを呼ぶだけにする。

これを守らないと、CI とローカルで検査内容がずれ、「CI でだけ落ちる」状態になる。

### ドキュメントを更新する

コマンドを追加したら、README とエージェント向け指示ファイルの記述も同時に更新する。
更新しなければ、次の診断で「ドキュメントとの乖離」として検出されることになる。

## エコシステム別の定石

具体的なツール選定は、**そのプロジェクトの言語で現在標準とされているもの**に従う。
迷ったら、リポジトリ内の既存の選択、同じエコシステムの主要プロジェクトの慣習、
公式ドキュメントの推奨を確認する。以下は出発点の目安。

- **JavaScript / TypeScript** — フォーマッタと linter は統合ツールに寄せるのが近年の傾向。型は厳格モードを既定とし、段階的に緩めない。テストランナーはビルドツールに統合されたものを優先
- **Python** — フォーマットと lint を単一の高速ツールにまとめる構成が主流。型チェックは別途。設定は言語標準のプロジェクト設定ファイルに集約する
- **Go** — 標準ツールチェーンで大半が揃う。追加するなら linter の集約ツール
- **Rust** — 標準ツールチェーンで揃う。lint の警告をエラー扱いにする設定を CI に入れる
- **複数言語・モノレポ** — 言語ごとに個別導入し、上位のタスクランナーで束ねる。変更のあった範囲だけ検査する仕組みが実行時間を左右する

いずれの場合も、**既に入っているツールと競合させない**。
フォーマッタと linter でスタイルルールが二重定義されているなら、統合するか、どちらかを無効にする。

## 項目別の要点

### CI の最小構成

初回はこれで十分。

- デフォルトブランチへの push と PR で起動
- 依存のインストール（キャッシュあり）
- フォーマットの検査 → lint → 型チェック → テスト
- 各ステップは失敗でジョブを落とす（失敗を無視する設定を付けない）

導入後に**必ず伝えること**: ブランチ保護で必須チェックに設定しないと、CI は通知にしかならない。
リポジトリ設定側の作業なので、ユーザーに依頼する。

マトリクスは、実際にサポートを表明しているバージョンのみに絞る。増やすほど遅くなる。

### git hook

配分を守る。

- **pre-commit** — 変更ファイルのみ対象。フォーマット適用、高速な lint、秘密情報の検出。数秒以内
- **pre-push** — 型チェック、unit test。数十秒以内
- それ以外はすべて CI

導入にはリポジトリで共有される hook 管理の仕組みを使う。`.git/hooks` への直接配置は、
クローンした環境に伝播しないので選ばない。

**遅い hook は必ず回避される。** 速度は品質の一部として扱う。

### テストの足がかり

テストが無いプロジェクトに「テストを書きましょう」と言っても動かない。次の順で提案する。

1. テストランナーを導入し、CI で実行される状態を作る（テストが 1 件でもよい）
2. 最も壊れやすい・最も重要なロジック 1 箇所にテストを書く
3. 直近の不具合があれば、その再現テストを書く（価値が最も分かりやすい）
4. 以降、機能追加にテストを伴わせる方針を合意する

カバレッジの閾値を設けるのは、ある程度テストが揃ってから。
最初から高い目標を置くと、意味のないテストを量産する動機になる。
閾値を入れる場合は、現在値をわずかに下回る値から始め、下げない運用にする。

e2e と mutation test は、下の層が整ってから。順序を飛ばさない。

### シークレットが見つかった場合

1. **鍵のローテーションを最優先で伝える。** 履歴に残っている以上、ファイルを消しても漏洩は取り消せない
2. 追跡から外し、`.gitignore` に追加する
3. `.env.example` に、値を伏せたキー名だけを置く
4. 履歴からの除去は履歴の書き換えを伴う。共有ブランチでは影響が大きいため、**必ず判断を仰いでから**行う。勝手に実行しない
5. 再発防止として、秘密情報の検出を pre-commit と CI に入れる

### エージェント向け指示ファイルの改善

書き足すのではなく、**まず削る**。コードを読めば分かることは価値が無く、長さは精度を下げる。

残すべき内容:

- ビルド・テスト・lint の実行方法（実在するコマンド）
- 非自明な制約と、その理由
- 触ってはいけない箇所
- そのプロジェクト特有の慣習

書かれたコマンドは、書いた後に実行して確かめる。

### 依存の自動更新

更新 bot を入れるときは、同時に運用方針を決める。
放置された PR が溜まる状態は、bot が無い状態より悪い（他の通知も無視されるようになる）。

- 更新をまとめる設定にして PR 数を抑える
- パッチ更新は CI が通れば自動マージ、メジャーは手動、といった区分を設ける
- CI が整っていない状態で bot を入れない。検証手段が無いまま更新 PR だけが増える

---

## 完了時

導入した項目ごとに報告する。

- 何を入れたか（追加・変更したファイル）
- 動作確認として実行したコマンドとその結果
- ユーザー側の作業が残っている場合はその内容（ブランチ保護の設定、鍵のローテーション、チーム内の合意など）
- 意図的に見送った範囲と理由
