# ba0918-rework 実装計画

## Goal

人が指定した範囲を診断し、見つけた問題を挙動の変わるものも含めて 1 件ずつ直し、1 件ごとに
テストで確かめて専用のブランチにコミットする単体スキル `ba0918-rework` が、このリポジトリの
`skills/` に入り、README から refactor との使い分けが分かる状態にする。

## Specification

`docs/spec/ba0918-rework.md`（コミット「docs: ba0918-rework の仕様と用語を追加」で承認）。
以下、節は `#見出し名` で示す。
この計画は仕様の文章を写さない。各ステップで挙げた節を、必ず仕様書そのもので読むこと。

用語（約束の変更、聞く項目、仕様のテスト、足場のテスト）の定義は `PROJECT.md` の Glossary 節の
「ba0918-rework」にある。仕様の本文もこれらの用語をこの意味で使っている。

## Approach and why

成果物はコードではなく、エージェントが読む指示文書（`SKILL.md` と `references/`）である。
書き方の制約は次の 5 つで、どれもこの計画の順番と書き方を決めている。

1. **本文は英語で書く。** `PROJECT.md` の「言語方針」による。仕様は日本語なので、実装は翻訳を伴う。
   仕様の日本語の言い回しを決まった文面として埋め込まず、意図を英語で書く。用語は次の英語に
   そろえ、本文の最初に出るところで短く定義する（Glossary の「呼ばない語」も英語側で守る）。
   - 約束の変更 → "contract change"（"breaking change" と呼ばない）
   - 聞く項目 → "ask item"
   - 仕様のテスト → "spec test"
   - 足場のテスト → "scaffold test"（"characterization test" と呼ばない）
2. **本文に名前を出してよいコマンドは git だけにする。** 仕様 `#移植性` による。テストの実行、
   依存のインストール、スクリーンショット、計測は、特定のツール名を出さずに「プロジェクトの
   テストを実行する」のように動作で書く。エージェント固有の仕組み（サブエージェントの機能名、
   ツール名）も書かない。他のスキルの名前（ba0918-refactor、レビューや調査の役目）は「これは
   このスキルの役目ではない」と境界を示すためだけに出してよく、読み込みや呼び出しを指示しない。
3. **このスキルはファイルを変え、コミットを作るスキルである。** 動き出す条件（`#動き出す条件`）を
   `description` と本文の両方に書く。`description` には、何をするスキルか、動き出す条件、
   refactor との違い（挙動を変える修正を認める）、ユーザーが実際に言いそうな言葉（英語と日本語）を
   書き、手順の中身は書かない。1024 文字以内に収める。
4. **観点ごとの手引きは `references/` に 1 観点 1 ファイルで置く。** 観点の絞り込み（`#入力`）が
   あるとき、見ない観点のファイルを読まずに済むからである。ファイル名は次のとおりにする。
   `bugs.md`、`design.md`、`performance.md`、`memory-leaks.md`、`security.md`、
   `spec-mismatch.md`。本文からは、診断でその観点を見るときに読むよう指示する。
5. **本文は ba0918-refactor の `SKILL.md` と同じ骨組みにする。** Scope、When edits may run、Rules、
   Procedure、Judgment、Examples、Evidence の並びである。同じ棚のスキルとして読み手が迷わない
   ようにするためで、中身は写さない（refactor は挙動を変えない前提で書かれており、そのまま使うと
   このスキルの規則と食い違う）。`PROJECT.md` の目安どおり、`SKILL.md` は 500 行以内に収める。

## Scope of change

- `skills/ba0918-rework/SKILL.md`（新規）
- `skills/ba0918-rework/references/` の 6 ファイル（新規、Approach の 4）
- `README.md`（スキル一覧への 1 行の追加のみ）

これ以外のファイルは変えない。仕様書と `PROJECT.md` の Glossary は承認済みなので触らない。
`skills/ba0918-rework/` に `scripts/`、`assets/` は作らない。

## Step order and prerequisites

作業は `ba0918-rework` ブランチで行う。このブランチがまだなければ、`main` の最新（仕様と計画の
コミットを含む）から作って切り替える。

1 → 2 → 3 → 4 → 5 → 6 → 7 の順に進める。

- Step 1 で骨組みと `description` を作り、バリデータの通過を先に確かめる。以降のステップはすべて
  この `SKILL.md` に書き足すので、frontmatter の誤りを最後に見つけると全部やり直しになるからである。
- Step 2 の観点の手引きを、Step 3 以降の手順より先に書く。手順の「診断」が手引きを読む指示を
  含むため、指すファイルが先にあるほうが突き合わせやすい。
- Step 3 の判断の規則（聞く項目、テスト、実測）を、Step 4 の手順より先に書く。手順の各段が
  これらの規則を参照するからである。
- Step 5 の報告は、報告に載せる区分が手順のどこで生まれるかが確定してから書く。
- Step 6 の README は、スキルの振る舞いが確定してから書く。
- Step 7 は全体の確認で、最後に行う。

コミットは各ステップで 1 つ作る。規則は次のとおり。

- ファイルは 1 つずつ名前を指定してステージする。`git add -A` や `git add .` は使わない。
- メッセージは日本語で、`<type>: <件名>` の形（Conventional Commits）。件名と本文には、変更の結果と
  理由を書く。「Step 2」のような計画の手順名や、作業の経緯は書かない。
- Step 7 で直すところがなければ、コミットは作らない。

## Left to the implementer

計画全体で任せること。どれを選んでも承認済みの振る舞いは変わらない。

- `SKILL.md` の中の見出し名、節の分け方（Approach の 5 の並びの範囲で）、英語の言い回し。
- `description` の具体的な文面（Approach の 3 の条件を満たす範囲で）。
- 観点の手引きの中身の構成（表か箇条か）と、挙げる典型例の選び方。例は仕様 `#観点` の N+1 の例を
  含める。
- 本文に添える例（Examples 節の良い例・悪い例、git のコマンド例）の選び方。例は意図の説明であり、
  決まった文面にしない。
- `<日時>` の書式（ブランチ名と worktree 名で同じ値を使い、ブランチ名として有効な文字だけを使う
  範囲で）。

## Stop conditions

次のときは作業を止め、何が起きたかを添えて引き渡す。

- 仕様の意味が決まっていない、または承認済みの内容から外れないと書けない箇所が見つかった。
- 仕様のとおりに書くと、`#移植性` に反して git 以外のツール名を本文に出さざるを得ない箇所が
  見つかった。
- 取り消せない操作・特権の要る操作・危険な対象への操作が必要になった。
- 同じ問題が別の場所にも広がっていると分かった。
- やり方を変えても先に進まない。

## Test command

コードのテストはない。各ステップの確認は次のコマンドと、ファイルを読んで仕様の節と突き合わせる
ことで行う。

- `agentskills validate ./skills/ba0918-rework`（`PROJECT.md` の Commands 表による）

## Out of scope

- `#人手確認チェックリスト` の実施。受け入れのときにユーザーが行う。
- ba0918-refactor の変更（見つけたバグの報告先として rework を案内するなど）。仕様にないため
  行わない。

## Step 1 — 骨組み、動き出す条件、入力

Purpose: スキルのディレクトリと frontmatter を作り、何をするスキルか・いつファイルを変えてよいか・
何を受け取るかを、`description` と本文の冒頭に書く。
Specification: [目的](../spec/ba0918-rework.md#目的)、[移植性](../spec/ba0918-rework.md#移植性)、
[動き出す条件](../spec/ba0918-rework.md#動き出す条件)、[入力](../spec/ba0918-rework.md#入力)、
[作らないもの](../spec/ba0918-rework.md#作らないもの)。
Prerequisites: `ba0918-rework` ブランチに切り替わっていること。
May change: `skills/ba0918-rework/SKILL.md`（新規）。
Done when:
1. frontmatter の `name` が `ba0918-rework` で、`description` が Approach の 3 を満たし、1024 文字
   以内である。
2. Scope の節が、このスキルが扱うこと（範囲の診断から、挙動を変える修正を含む 1 件ずつの修正・
   確かめ・コミットまで）と、扱わないこと（診断だけの依頼、挙動を変えない整理＝refactor の役目、
   マージ・push・issue の起票・worktree の削除、範囲の外の修正）を述べている。
3. 最優先の方針（人への確認を増やさない）と、そのかわりの安全網 2 つ（ブランチへの 1 件ずつの
   コミット、報告の根拠と実測）が書かれている。
4. When edits may run の節に、`#動き出す条件` の 2 つの「動かない場合」が書かれている。
5. 入力 3 つ（範囲、観点の絞り込み、事前の許可）と、範囲が解決できないとき何も変えずに理由を返す
   こと、大きすぎるときの止め方（固定の線を引かない判断と、理由を分割の提案に書くこと）、件数の
   上限を設けないことが書かれている。
6. `agentskills validate ./skills/ba0918-rework` が `Valid skill: ...` を返す。
Shown by: artifact — `skills/ba0918-rework/SKILL.md`。6 はコマンドの出力、1 の文字数は frontmatter の
`description` の値の文字数を数えて確かめ、2〜5 はファイルを読んで仕様の節と突き合わせる。
Left to the implementer: なし（計画全体で任せたことを除く）。
Stop and hand back if: `description` に Approach の 3 の要素をすべて入れると 1024 文字に収まらない。

## Step 2 — 観点の手引き

Purpose: 6 つの観点それぞれについて、見つけ方と、直すときの落とし穴を `references/` に書き、
本文の診断の段からそれを読むよう指示する。
Specification: [観点](../spec/ba0918-rework.md#観点)、[移植性](../spec/ba0918-rework.md#移植性)。
Prerequisites: Step 1。
May change: `skills/ba0918-rework/references/` の 6 ファイル（Approach の 4 の名前で新規）、
`skills/ba0918-rework/SKILL.md`。
Done when:
1. 6 ファイルがあり、それぞれに見つけ方（典型的な兆候）と、直すときの落とし穴（挙動の変化を
   宣言の外に漏らす典型）がある。`performance.md` に N+1 と、まとめて読み込むと結果の順序が
   変わる落とし穴がある。
2. `spec-mismatch.md` に、仕様として扱うもの（`#観点` の 5 種）が書かれている。
3. `design.md` に、設計の問題は問題を直すための構造の変更として扱い、読みやすさのための小さな
   変形（refactor の役目）とは違うことが書かれている。
4. `SKILL.md` の本文から 6 ファイルへの参照が、スキルのルートからの相対パスで書かれ、観点の
   絞り込みがあるときは見る観点のファイルだけを読むよう指示している。
5. 手引きに、git 以外のツール名、特定の言語やフレームワークだけで通じる指示がない（典型例として
   言語やフレームワークの名前を挙げるのはよい）。
6. `agentskills validate ./skills/ba0918-rework` が `Valid skill: ...` を返す。
Shown by: artifact — `skills/ba0918-rework/references/*.md`、`skills/ba0918-rework/SKILL.md`。
6 はコマンドの出力、1〜5 はファイルを読んで仕様の節と突き合わせる。
Left to the implementer: 各ファイルの長さと構成、挙げる典型例。
Stop and hand back if: なし。

## Step 3 — 聞く項目、テスト、実測の規則

Purpose: 何を人に聞き何を LLM が決めるか、テストの 2 種類とその扱い、実測が要る項目の確かめ方を、
本文の Rules と、それを説明する Judgment に書く。
Specification: [聞く項目の扱い](../spec/ba0918-rework.md#聞く項目の扱い)、
[テスト](../spec/ba0918-rework.md#テスト)、[実測が要る項目](../spec/ba0918-rework.md#実測が要る項目)、
[人の判断点](../spec/ba0918-rework.md#人の判断点)。
Prerequisites: Step 2。
May change: `skills/ba0918-rework/SKILL.md`。
Done when:
1. 聞く項目が 2 種類（約束の変更、根拠から決められない項目）に限られ、それ以外の振る舞いの変化は
   根拠を示して直すこと、根拠になるもの、「根拠が割れた」の判定（出典どうしが食い違い、優先の
   根拠もない）、仕様の文書のほうを直す場合、セキュリティで入力を拒む場合の境界、公開 API の
   形の変更と削除が約束の変更であることが書かれている。
2. 聞く項目を、聞く項目でない項目をすべて直した後に一回だけまとめて聞くこと、各項目に付けるもの
   （何が変わるか、根拠、推奨）、答えを得たら続けて直すこと、聞く項目を土台とする項目の扱い
   （答えを待つ、「直さない」のとき、人が答えられない実行のとき）が書かれている。
3. 事前の許可の 2 つの形と、「すべて推奨どおり」が根拠から決められない項目にも及ぶこと、
   人が答えられない実行では聞く項目を直さず推奨付きで報告することが書かれている。
4. 仕様のテストと足場のテストの定義と扱い（足場はコミットせず項目を終えたら消す、仕様の根拠と
   一致すれば格上げしてその項目のコミットに含める）、後付けのテストを仕様として残さない理由、
   期待値を変えてよい範囲と参照の更新の扱い、テストが書けない場合の保留と、文書だけの修正・
   削除がその対象外であることが書かれている。
5. 性能とメモリの前後比較、一時的な計測の仕組みを作ってよくコミットしないこと、UI の見た目は
   約束の変更として答えか許可を得てから直し、前後のスクリーンショットで宣言外の変化がないことを
   確かめ、確認は待たないこと、手段がなければ保留することが書かれている。
6. Approach の 1 の英語の用語が使われ、最初に出るところで定義されている。
7. 範囲が大きいとき読むだけの診断は別のコンテキストに任せてよく、編集は呼び出されたセッションが
   行うこと（`#入力`）が、特定のエージェントの機能名を出さずに書かれている。
8. `agentskills validate ./skills/ba0918-rework` が `Valid skill: ...` を返す。
Shown by: artifact — `skills/ba0918-rework/SKILL.md`。8 はコマンドの出力、1〜7 はファイルを読んで
仕様の節と突き合わせる。
Left to the implementer: 規則を Rules と Judgment のどちらに置くかの配分（規則そのものは Rules に、
理由は Judgment に置く範囲で）。
Stop and hand back if: なし。

## Step 4 — 作業場所と手順

Purpose: 診断から最後の全体テストまでの手順を、作業場所の作り方、直す順番、1 件ずつの進め方、
削除、範囲の外の扱いを含めて Procedure に書く。
Specification: [作業場所](../spec/ba0918-rework.md#作業場所)、[直す順番](../spec/ba0918-rework.md#直す順番)、
[1 件ずつ直す](../spec/ba0918-rework.md#1-件ずつ直す)、[削除](../spec/ba0918-rework.md#削除)、
[範囲の外](../spec/ba0918-rework.md#範囲の外)、[外部依存](../spec/ba0918-rework.md#外部依存)、
[入力](../spec/ba0918-rework.md#入力)。
Prerequisites: Step 3（手順が規則を参照するため）。
May change: `skills/ba0918-rework/SKILL.md`。
Done when:
1. 手順の並びが次のとおりである。範囲を決める → 読むだけの診断（ブランチを作らない） → 直す項目が
   1 件以上あれば worktree とブランチを作る → 依存のインストールと基準の全体テスト → 聞く項目で
   ない項目を順に 1 件ずつ直す → 聞く項目をまとめて聞いて直す → 最後の全体テスト → 報告。
2. 作業場所について、ブランチ名 `rework/<日時>`、worktree を HEAD から作ってリポジトリと同じ親
   ディレクトリに `<リポジトリ名>-rework-<日時>` の名前で置くこと、一時ディレクトリに置かない理由、
   元の作業ツリーに一切触れないこと（ブランチの切り替えも stash もしない）、元の未コミットの変更は
   診断の対象外と報告すること、未コミットの変更を理由に確認しないこと、基準の全体テストが実行
   できなければ何も直さず止めること、マージ・push をせず worktree を残すことが書かれている。
3. 直す順番（依存の定義、重要度の順、データ破壊が観点をまたぐ属性であること、1 件ごとに残りを
   見直し、消えた項目を記録すること）が書かれている。
4. 1 件ずつの 6 段（宣言、テスト、修正、対象のテストとチェック、1 コミット、新たな失敗なら戻して
   保留）が書かれ、「対象のテストを絞れなければ全体」と、コミットメッセージをプロジェクトの規約に
   従わせることが含まれている。
5. 基準の全体テストと「新たに失敗した」の定義、最後の全体テストで新たな失敗があれば二分探索で
   原因のコミットを特定し、依存する後ろのコミットごと新しい順に取り消して保留し、再実行して
   なくなるまで繰り返すことが書かれている。
6. 削除の条件（確かめる 3 点）、公開 API は聞く項目、確かめきれなければ削除せず報告すること、
   範囲の外の同じ問題は直さず場所を報告することが書かれている。
7. 範囲が大きいとき読むだけの診断は別のコンテキストに任せてよく、編集は呼び出されたセッションが
