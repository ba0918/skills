# 診断項目の判定基準

各項目について「何を集めるか」「形骸化のサイン」「必要度の決め方」を示す。
必要度は既定値であり、プロファイリングの結果で上下させてよい。ただし変えた場合は理由を述べる。

---

## 1. .gitignore

### 集める証拠

- `.gitignore` の内容。グローバル gitignore や `.git/info/exclude` に頼っていないか
- **追跡してはいけないものが追跡されていないか**（本題はこちら）
  - ビルド成果物、依存ディレクトリ、キャッシュ、ログ、エディタ・OS 固有ファイル
  - `.env` などの秘密情報を含みうるファイル（項目 10 と接続）
  - 追跡済みファイルの一覧を出し、サイズの大きいファイルや生成物らしき拡張子を探す
- リポジトリのサイズと、履歴中の巨大ファイル
- 逆方向の事故: 必要なファイルが誤って除外されていないか（`.env.example`、設定サンプル、空ディレクトリの `.gitkeep`）

### 形骸化のサイン

- パターンは書かれているが、それ以前にコミットされたファイルが追跡され続けている
  （`.gitignore` は追跡済みファイルには効かない。これは頻出する見落とし）
- 使っていない言語のテンプレートが延々と貼られている一方、実際に使うツールの出力が漏れている
- `git status` に常に大量の未追跡ファイルが出ていて、変更の確認が実質できない状態

### 必要度

常に**必須**。ただし所見が無ければ 1 行で終える。

## 2. エージェント向け指示（AGENTS.md / CLAUDE.md 等）

### 集める証拠

- ルートおよびサブディレクトリの指示ファイル。複数ある場合は重複と矛盾
- 記述されているコマンドが**実在するか**。書かれたテスト・ビルドコマンドを実際に実行して確かめる
- 記述されているディレクトリ構成が現状と一致するか
- 最終更新日と、その後のリポジトリの変化量（指示ファイルの更新以降のコミット数）
- 内容の質:
  - コードを読めば分かることの列挙に終始していないか（低価値）
  - 守るべき制約、非自明な決まり、やってはいけないことが書かれているか（高価値）
  - ビルド・テスト・lint の実行方法が書かれているか

### 形骸化のサイン

- 書かれたコマンドが存在しない、または失敗する（**最も多い**）
- 参照しているファイル・ディレクトリが移動・削除されている
- 生成されたまま一度も更新されていない（作成コミット以降、変更が無い）
- 汎用的な心得だけで、そのプロジェクト固有の情報が無い

### 必要度

エージェントによる作業が行われている、または行う予定なら**必須**。
それ以外では**推奨**（人間のオンボーディング文書としても機能する）。

---

## 3. フォーマッタ

### 集める証拠

- フォーマッタの設定（そのエコシステムの標準的なもの。設定ファイル、またはマニフェスト内の設定セクション）
- **実際に実行して差分が出るか**。チェックモードで走らせ、未整形のファイル数を数える
- CI で検証されているか、hook で自動適用されているか
- `.editorconfig` の有無と、フォーマッタ設定との矛盾
- 改行コード設定（`.gitattributes`）。複数 OS の環境で問題になる

### 形骸化のサイン

- 設定はあるが、チェックモードで大量のファイルが引っかかる（誰も実行していない）
- CI にも hook にも組み込まれておらず、各自の手動実行に依存している
- linter とフォーマッタでスタイルルールが二重定義され、互いに競合している
- 除外設定が肥大化し、実質的にほとんどのコードが対象外になっている

### 必要度

複数人が触るなら**必須**。単独開発でも**推奨**（差分ノイズが減り、レビューとエージェントの作業が楽になる）。
ドキュメントのみのリポジトリでは**任意**。

---

## 4. linter

### 集める証拠

- linter の設定と、有効になっているルールセットの範囲（推奨セットか、最小限か）
- **実際に実行した結果**。error と warning の件数
- 抑制の使われ方: インラインの無効化コメントの数と分布。特定ファイルに集中しているか、全体に散っているか
- 除外設定の範囲
- CI で実行され、失敗が**ビルドを落とすか**
- warning を許容する設定になっているか（許容上限の指定があるか）

### 形骸化のサイン

- warning が数百件出ているが CI は緑（＝警告に意味が無くなっている）
- 抑制コメントが理由の記載なく多用されている
- error のみ検査し、実質的にルールがほぼ無効
- 導入されているが最後の設定変更が非常に古く、以後追加されたコードの傾向を捉えていない

### 必要度

コードのあるプロジェクトでは**必須**。
ただしフェーズがプロトタイプなら、最小構成（明らかなバグ検出のみ）に留めることを勧める。

## 5. 型チェック・静的解析

linter とは別枠で見る。lint より効くのに、lint があることで満足して抜けやすい。

### 集める証拠

- 型システムの利用状況と厳格度の設定（厳格モードが有効か、段階的に緩められているか）
- **実際に型チェックを実行した結果**のエラー件数
- 型の抜け穴の使用状況: 動的型への逃げ、型アサーション、型検査の無効化コメントの数
- 型定義の欠落（依存ライブラリの型情報が無く、暗黙に動的型になっていないか）
- CI で型チェックが実行されるか
- 型システムを持たない言語の場合、代替の静的解析（データフロー解析、複雑度検査など）が使われているか

### 形骸化のサイン

- 厳格モードが導入時から無効のまま
- 型チェックがローカルでは通らないが、CI に無いので誰も気付いていない
- 逃げ道の記述が広範に散っており、型による保証が実質的に無い
- エディタ上でのみ検査され、CI で強制されていない

### 必要度

型システムを持つ言語なら**必須**。
持たない言語では**任意**（規模が大きい、または運用中なら**推奨**）。

## 6. テスト

### 集める証拠

まず**種別ごとに**存在を確認する。

- **unit** — テストファイルの数、ソースファイル数との比
- **integration** — 実際の依存（DB、外部 API、ファイルシステム）を伴うテストがあるか。テスト用コンテナ等の設定
- **e2e** — ブラウザ／CLI／API を外側から叩くテスト
- **mutation** — テストの品質を検査する仕組み

そのうえで運用実態を見る。

- テストコマンドが**実際に通るか**。落ちているテストや skip の数
- カバレッジの計測有無、数値、そして**CI で閾値を強制しているか**
- CI でテストが実行されているか。実行時間
- 直近のコミットで、機能追加にテストが伴っているか（プロダクトコードだけ変わるコミットの割合）
- テストの質: assert の無いテスト、常に真になる assert、実装をそのまま写しただけのテスト
- flaky の兆候: 再実行の設定、無効化されたテスト、無効化理由のコメント

### 形骸化のサイン

- テストは存在するが CI で実行されていない（**最も多い**）
- 落ちているテストが放置され、常に無視されている
- skip / 無効化されたテストが積み上がっている
- カバレッジを計測しているが閾値を設けておらず、下がり続けている
- e2e が flaky で、再実行前提の運用になっている、または CI から外されている
- ハッピーパスのみで、エラー処理や境界値のテストが皆無

### 必要度

- **unit** — 実験・使い捨て以外は**必須**
- **integration** — 外部依存があるなら**推奨**。運用中なら**必須**
- **e2e** — 利用者が触る UI やインタフェースがあり、運用中なら**推奨**。それ以外は**任意**（維持コストが高いため、安易に勧めない）
- **mutation** — **任意**。次の条件がすべて揃うときのみ勧める: unit test が十分あり、カバレッジも高く、それでも不具合が漏れている。カバレッジが低い段階で勧めるのは順序が間違っている

## 7. git hook

### 集める証拠

- hook の管理方法（hook 管理ツール、または `.git/hooks` への直接配置）
  - `.git/hooks` に直接置かれている場合、**それはリポジトリに共有されていない**。他の開発者やクローンした環境では効かない
- pre-commit / pre-push それぞれの中身
- **各 hook の実行時間**。実際に走らせて測る
- コミット履歴に hook を回避した形跡がないか（hook を通れば起きないはずの違反が commit されているか。例えば pre-commit でフォーマットしているのに未整形のコミットがある）
- hook で検査している内容が CI にもあるか（**hook にしか無い検査は、実質強制力が無い**）

### 形骸化のサイン

- pre-commit が重い（数秒を大きく超える）。全テストを走らせる構成は典型的な失敗
  — 重い hook は必ず回避されるので、ゲートとして機能していないと判定する
- `.git/hooks` 直置きで、共有されていない
- 検査対象が全ファイルで、変更ファイルに絞られていない
- hook で検査しているが CI に同じ検査が無い（ローカルで回避すれば素通り）
- 常に失敗するため全員が回避オプションを付けて運用している

### 適切な配分

これが判定の軸になる。

| タイミング | 適する検査 | 目安 |
|---|---|---|
| pre-commit | 変更ファイルのフォーマット、高速な lint、秘密情報の検出 | 数秒以内 |
| pre-push | 型チェック、unit test | 数十秒以内 |
| CI | 全検査。テスト全種別、ビルド、依存の監査 | 制約なし |

hook はローカルで回避できるため、**品質の最終的な保証は必ず CI 側に置く**。hook は「CI に落とされる前に気付くための時間短縮」であり、ゲートそのものではない。

### 必要度

**推奨**。ただし CI が未整備なら、hook より CI を先に勧める。優先順位を逆にしない。

## 8. CI

### 集める証拠

- CI 設定ファイルの有無と、実行される検査の内訳
- **直近の実行結果**。デフォルトブランチが緑か。失敗しているなら、いつからか
- 実行時間、および目立って遅いステップ
- 対象となるイベント（PR、デフォルトブランチへの push、タグ）
- ブランチ保護と連動しているか（**成功が必須チェックとして設定されているか**）。これが無ければ CI は単なる通知
- 依存のキャッシュ、ジョブの並列化
- 検査ごとの網羅: フォーマット / lint / 型 / テスト各種 / ビルド / 依存監査
- マトリクスの妥当性（サポートするランタイムのバージョンを実際に検査しているか）
- CI 内で使う外部アクション・イメージのバージョン固定
- CI にのみ存在してローカルから実行できない検査がないか（あると開発者は事前に確認できない）

### 形骸化のサイン

- デフォルトブランチが長期間 red のまま
- 必須チェックになっておらず、落ちたままマージできる
- 検査ステップに失敗を無視する設定が付いている
- 遅すぎて（十数分以上）、結果を待たずにマージされる運用になっている
- ローカルの検査と CI の検査が食い違っており、片方だけ通る

### 必要度

複数人が触る、または運用中なら**必須**。単独開発でも**推奨**（自動検査の置き場所として最も確実）。
実験・使い捨てなら**不要**。

---

## 9. 依存関係の健全性

### 集める証拠

- **ロックファイルがコミットされているか**。アプリケーションなら必須、ライブラリならエコシステムの慣習に従う
- ロックファイルとマニフェストの整合（マニフェストだけ更新されていないか）
- 既知の脆弱性。エコシステム標準の監査コマンドを実行し、深刻度別に件数を出す
- 更新の停滞: 大きく古くなっている依存、サポートの切れたもの
- 自動更新の仕組み（更新 bot の設定）の有無と、**その PR が放置されていないか**
- 依存の総数と、明らかに不要なもの（未使用の依存）
- ライセンスの整合（公開・配布物の場合）

### 形骸化のサイン

- ロックファイルが gitignore されている
- 更新 bot の PR が何十件も未処理で溜まっている（**bot はあるが機能していない典型**）
- 監査コマンドが CI にあるが、失敗を無視する設定になっている
- 深刻度の高い脆弱性が長期間放置されている

### 必要度

外部依存があるなら**必須**。脆弱性監査は、公開または運用中なら**必須**、それ以外は**推奨**。

## 10. シークレット管理

### 集める証拠

- 追跡されているファイルに秘密情報が含まれていないか
  - `.env`、資格情報ファイル、鍵ファイルが追跡されていないか
  - ソース中のハードコードされた鍵・トークン・パスワード・接続文字列
  - 設定ファイル、テストのフィクスチャ、ドキュメント中のサンプルも見る（**見落としやすい**）
- **コミット履歴**に秘密情報が残っていないか（現在のファイルから消えていても履歴には残る）
- `.env.example` など、必要な環境変数を示すファイルがあるか
- CI で使う秘密情報が、設定ファイルに直書きされず秘密管理機構経由になっているか
- 秘密情報の検出ツール、またはリポジトリホスティング側のスキャン機能が有効か

### 形骸化のサイン

- `.gitignore` に `.env` があるが、以前にコミットされた `.env` が追跡され続けている
- サンプル値と称して実在の値が `.env.example` に入っている
- 検出ツールの設定はあるが、除外リストで実質的に無効化されている

### 報告時の注意

**実際の秘密情報の値をレポートに書かない。** ファイル名と行番号、種別のみを示す。
発見した場合は、削除だけでなく**鍵のローテーションが必要**である旨を必ず伝える
（履歴に残っている以上、消しても漏洩は取り消せない）。

### 必要度

常に**必須**。ただし所見が無ければ 1 行で終える。

## 11. 環境の再現性

### 集める証拠

- **ランタイムのバージョン指定**があるか（バージョン管理ツール用のファイル、マニフェスト内のエンジン指定、コンテナイメージのタグ）
- 指定が複数箇所にあり、食い違っていないか（マニフェスト・CI・コンテナ・ドキュメントで別々のバージョンを指しているのはよくある）
- **README のセットアップ手順が実際に通るか**。手順どおりに実行してみる
- 開発環境のコンテナ定義や、環境構築スクリプトの有無
- `.editorconfig`
- 必要な外部サービス（DB など）をローカルで立てる手段があるか
- 「動かすまでに必要な手数」。手順が 5 つを超えるなら、それ自体が所見

### 形骸化のサイン

- README の手順が古く、途中で失敗する
- バージョン指定が箇所ごとに違う
- ローカルでは動かず CI でしか検証できない
- セットアップの暗黙知が特定の人にしか無い（README に無い手順が必要）

### 必要度

複数人が触る、またはエージェントが作業するなら**必須**。
単独・短期なら**推奨**。

- [ ] プロファイリングを行い、必要度をプロジェクトに合わせて調整したか
- [ ] 設定ファイルを読むだけでなく、**コマンドを実行**したか
- [ ] CI の直近の実行結果を確認したか
- [ ] 各所見に、観測した事実（ファイル名・行・出力・状態）の根拠があるか
- [ ] 「不要」と判断した項目に理由を書いたか
- [ ] 形骸化している項目を、未整備の項目より上に置いたか
