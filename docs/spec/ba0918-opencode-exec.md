# ba0918-opencode-exec 仕様

## 目的

タスクのやり方を決めるスキルと、そのタスクを誰に実行させるかを分けて、小さなスキルの
組み合わせで複雑な作業を組み立てられるようにする。このスキルはその「誰に実行させるか」の
側の 1 つで、opencode CLI を通して、別の提供元のモデルにタスクを 1 つ実行させる。

一文でいえば: 呼び出し元が用意したプロンプトと環境で `opencode run` を 1 回実行し、
終了コード、出力のファイル、変更一覧を返す。

このスキルは [実行役スキル](../../PROJECT.md#glossary) である。プロンプトの中身を書かず、
結果の良し悪しも判定しない。読み取り専用にするか、どの worktree で動かすか、どの権限を
与えるかといった環境の用意は、呼び出し元（メインセッション）の責務であり、このスキルは
制御しない。

用語（実行役スキル、前置きのコマンド、変更一覧）の定義は `PROJECT.md` の Glossary 節にある。

各要件の確認方法は、末尾の [人手確認チェックリスト](#人手確認チェックリスト) の項目番号で示す。

### 移植性

opencode CLI と git は、このスキルの扱う対象と変更一覧の手段なので本文に書く。それ以外は、
特定のエージェント、モデル、実行環境の仕組みに依存しない自然言語で書く。他のスキルにも
依存しない。環境ごとの値（サンドボックスのポリシーファイルのパス、モデル名の既定値、
ホームディレクトリ配下のパス）や、特定のサンドボックスの名前は本文に書かない。

- 成功条件: `agentskills validate ./skills/ba0918-opencode-exec` が通る。本文に opencode と git
  以外の固有のツール名や API 名、絶対パス、特定の利用者の環境の値が現れない（人が本文を読んで
  確認する）（C-01）。
- 反例: 本文にサンドボックスのポリシーファイルの絶対パスが書かれている。「Bash ツールの
  run_in_background で」と書かれている。

### 実行してよい条件

実行するのは、ユーザーが名指ししたとき、またはユーザーが用意した指示（割り当て表、
ローカルの組み合わせスキル、指示ファイルなど、形は問わない）がこの実行役を名指ししたとき
だけである。タスクのスキルが読み込まれた、opencode の話題が出た、というだけでは実行しない。
この条件を、説明文（description）と本文の両方に書く。

- 成功条件: 説明文と本文の両方に、名指しされたときだけ実行することが書かれている（人が読んで
  確認する）。opencode について質問しただけの会話で `opencode run` が実行されない。ユーザーの
  直接の名指しと、指示ファイルに書いた名指しの両方で実行される（C-02）。
- 反例: 「opencode ってどう使うの？」という質問に対して `opencode run` を起動する。

### 外部への送信の明示

作業ディレクトリの内容と、プロンプトの中身が、選んだモデルの提供元に送られる。
名指しされた時点で送ってよいと判断済みとみなし、実行前に改めて確認しない。そのかわり、
送られることを説明文と本文の両方に書く。

- 成功条件: 説明文と本文の両方に、内容が選んだモデルの提供元に送られることが書かれている
  （人が読んで確認する）。名指しされた実行で、送信の確認を挟まずに実行が始まる（C-02）。
- 反例: 説明文に送信のことが書かれておらず、利用者が入れてから初めて気づく。

### 呼び出し元が渡すもの

| 渡すもの | 必須か | 内容 |
|---|---|---|
| プロンプトのファイル | 必須 | それだけで完結したタスクの指示 |
| モデル | 必須 | `provider/model` または `provider/model#variant` |
| 作業ディレクトリ | 任意 | 既定は現在の作業ディレクトリ。worktree を用意したならそのパス |
| エージェント名 | 任意 | opencode の設定で定義したエージェント。権限の設定を効かせるときに使う |
| [前置きのコマンド](../../PROJECT.md#glossary) | 任意 | サンドボックスの起動などのコマンド列。単語の並び（引数のリスト）で受け取る |
| コマンド名 | 任意 | 既定は `opencode`。v2 を別名で入れている環境ではその名前 |
| 変更禁止 | 任意 | この実行で作業ディレクトリを変えてはいけないこと。既定はなし |
| 時間の上限 | 任意 | 既定はなし |
| 出力の置き場所 | 任意 | 既定は一時ディレクトリ。まだ存在しなければスキルが作る |

次のときは実行せず、何が足りないか・何がおかしいかを返す。

- 必須のものが渡されていない
- プロンプトのファイルが存在しない、空である、または読めない
- 作業ディレクトリが存在しない
- 出力の置き場所が作業ディレクトリを含むリポジトリの中にある。作業ディレクトリが git の管理下に
  なければ、作業ディレクトリの中にある（黙って別の場所に変えると、呼び出し元がファイルを
  見つけられなくなるため）

モデルの書き方はスキルでは検査しない。誤っていれば opencode がエラーを返し、それを結果として返す。

- 成功条件: モデルを渡さずに呼ぶと、実行されず、モデルが足りないと返る。存在しないプロンプトの
  ファイルを渡しても同様に返る。出力の置き場所に作業ディレクトリの中を渡すと、実行されず、
  その理由が返る（C-03）。
- 反例: モデルが渡されないとき、スキルが自分で適当なモデルを選んで実行する。作業ディレクトリの
  中を指定された出力の置き場所を、黙って一時ディレクトリに変える。

### 実行前の確認

実行の前に次を行う。

1. 前置きのコマンドを付けてコマンド名の `--version` を実行し、表示された版番号のメジャーが 2
   でなければ、実行せずにその旨と見つかった版を返す。コマンドが見つからない場合も同様に返す。
   前置きを付けるのは、サンドボックスの中で別の版が解決される食い違いを防ぐためである。
2. 作業ディレクトリが git の管理下なら、それを含むリポジトリ全体の状態を記録する。記録するのは、
   その時点のコミット（HEAD）、変更のあるファイル・無視されていない未追跡のファイルの一覧、
   それぞれの中身を比べられる値（ハッシュ）である。記録は出力の置き場所のファイルに書き、
   会話には置かない。git の管理下でなければ記録しない。

v1 はフラグの体系が違い、`--standalone` を持たない。意味の違うフラグのまま動くのを防ぐため、
v1 では実行しない。

- 成功条件: v1 の opencode をコマンド名として渡すと、実行されず、v2 が必要なことと見つかった版が
  返る（C-04）。
- 反例: v1 に対して v2 のフラグで実行し、エラーの出力をそのまま結果として返す。前置きの外で版を
  確認し、サンドボックスの中では別の版が動く。

### コマンド

実行するコマンドは次の形である。

```
[前置きのコマンド] <コマンド名> run --standalone --auto --model <モデル> [--agent <エージェント名>] <プロンプトのファイルの中身>
```

- 作業ディレクトリで実行する。
- 前置きのコマンドは解釈せず、受け取った単語の並びを、並びも中身も変えずに前に付ける。
  1 本の文字列として渡されたときも、スキルが空白で分けたりシェルに解釈させたりせず、1 つの単語として
  そのまま付ける。
- `--standalone` は常に付ける。付けないと作業が opencode のバックグラウンドサービスに渡り、
  前置きのコマンドが作ったサンドボックスの外で動く（2026-09-23 に計測）。
- `--auto` は常に付ける。付けないと、裏で実行している途中の権限確認で止まる可能性がある
  （推測、未確認）。`--auto` は、設定で明示的に拒否されていない権限をすべて自動で許可する。
  このことを、どの実行でも結果とともに伝える。
- プロンプトは、ファイルの中身をシェルに解釈させずに 1 つのメッセージ引数として渡す。
  `--file` での添付は使わない。ファイルは、何を頼んだかの記録として残す。
- 中身の先頭が `-` のプロンプトは、フラグとして読まれるおそれがあるため、実行せずにその理由を
  返す。
- 中身が長すぎて起動できなかったときは、その旨を返す。別の渡し方に切り替えない。
- stdout と stderr は、出力の置き場所に、実行ごとに異なる名前（日時と乱数を含む）のファイルで
  書く。既存のファイルは上書きしない。

- 成功条件: 前置きのコマンドとエージェント名を渡した実行で、実際に起動されたコマンドが上の
  形になっている（引数を表示してから本物に渡す前置きのコマンドを使って人が確認する）。
  引用符や `$` を含むプロンプトが、そのままの文字列で届く（C-05）。先頭が `-` のプロンプトは
  実行されずに理由が返る（C-03）。
- 反例: `--standalone` を付けずに実行する。前置きのコマンドの中身を書き換えたり、一部だけを
  使ったりする。プロンプトの中の `$HOME` が展開されて届く。

### 実行と待機

実行は、セッションが終了を待てる形で行い、終了するまで待つ。長い実行（数十分）でも、
途中で状態を確かめるために実行を止めたり起動し直したりしない。

時間の上限が渡されたときだけ、それを超えたら、このスキルが起動したプロセスとその子孫を
すべて止める。前置きのコマンドだけを止めて、中の opencode が書き込みを続けるのを防ぐためで
ある。ほかのプロセスは止めない。止めた後で変更一覧を作り、結果には時間切れであることを明記
して、そこまでの stdout・stderr のファイルと変更一覧を返す。

前置きのコマンドによっては、opencode がこのスキルの起動したプロセスの子孫にならない（別の
サービスに起動を頼むなど）。止めた後に子孫が残っていないことを確かめられなかったときは、
opencode がまだ動いていて、変更一覧の後にも書き込みが続くかもしれないことを、時間切れの明記と
あわせて結果に書く。

- 成功条件: 数分かかる調査を頼み、途中で止めたり起動し直したりせずに、終了後に結果が返る
  （C-09）。上限を短く渡した実行で、上限を過ぎたところで止まり、時間切れと明記された結果が
  返る。前置きのコマンドの中の opencode も止まっている。同時に動かしておいた別の opencode の
  プロセスは止まらない（C-06）。
- 反例: プロセス名で opencode をまとめて止める。前置きのコマンドだけを止める。時間切れを通常の
  終了として返す。子孫が残っていないことを確かめられないのに、止まったものとして返す。

### 変更一覧

実行が終わったら（終了コードが 0 でも 0 以外でも、時間切れでも）、実行前の記録と比べて
[変更一覧](../../PROJECT.md#glossary) を作る。

- 対象は、作業ディレクトリを含むリポジトリ全体の、git から見えるファイル（追跡中のファイルと、
  無視されていない未追跡のファイル）である。git で無視されたファイルは対象外で、そのことを
  結果に書く。
- 実行前と実行後の状態だけを比べる。実行前から変更のあったファイルも、中身が変わっていれば
  入れる。実行中に変わって元に戻ったファイルは入れない。
- HEAD が実行前から動いていれば、そのことと、前後のコミットの間で変わったファイルを入れる。
- 誰が変更したかは区別しない。区別が要るなら、呼び出し元がディレクトリを分ける。

変更は戻さない。

- 成功条件: 実行前から未コミットの変更があるファイルを、プロンプトでさらに書き換えさせると、
  そのファイルが変更一覧に入る。新しいファイルを作らせると、それも入る。ファイルを変えて
  コミットまでさせると、HEAD が動いたことと、そのファイルが入る（C-07）。
- 反例: `git status` の表示が前後で同じだからといって、中身の変わったファイルを変更一覧から
  落とす。コミットされた変更を見落として「変更なし」と返す。変更を見つけて自動で元に戻す。

### 返すもの

結果として次を返す。要約や良し悪しの判定はしない。

- 終了コード（時間切れのときはそのこと）
- stdout のファイルのパス
- stderr のファイルのパス
- 変更一覧と、それが「開始から終了までにリポジトリの git から見えるファイルで起きた変更で、
  誰の変更かは区別せず、無視されたファイルは含まない」ものであること（git の管理下でなければ、
  検出できなかったこと）
- `--auto` で、設定で拒否されていない権限は自動で許可されたこと

前置きのコマンド自体の失敗と opencode の失敗は区別しない。どちらも終了コードと stderr で返す。

変更禁止が渡された実行では、ほかの結果より先に次を伝える。

- 変更一覧が空でなければ、変更が起きたこと
- git の管理下でなければ、変更を検出できないこと

stdout は opencode の既定の出力形式のまま書く（`--format json` は使わない）。

- 成功条件: 変更禁止を渡してファイルを書き換えさせる実行で、結果の最初に変更が起きたことが
  書かれている（C-07）。git の管理下でない場所で変更禁止を渡すと、結果の最初に検出できない
  ことが書かれている（C-08）。どの実行の結果にも上の 5 点がある（C-05）。
- 反例: stdout の内容を要約して「問題はありませんでした」と返す。変更が起きたこと、または
  検出できないことを、出力の説明の後ろに埋もれさせる。

### 出力ファイル

stdout・stderr のファイルと実行前の記録は、出力の置き場所に置く。出力の置き場所がまだ存在
しなければ、スキルが作る（置き場所がリポジトリや作業ディレクトリの中なら実行しないため、作る
場所はその外に限られる）。スキルはこれらのファイルを
消さない。消すのは呼び出し元かユーザーである。

- 成功条件: 出力の置き場所を渡さない実行で、ファイルが作業ディレクトリの外にでき、実行後も
  残っている。同じ置き場所で 2 回実行して、1 回目のファイルが上書きされていない（C-05）。
- 反例: 結果を返した後にファイルを消す。2 回目の実行が 1 回目の stdout を上書きする。

## 作らないもの

- 読み取り専用の強制、worktree の用意、権限の設定。環境の用意は呼び出し元の責務である。
- タスク用のプロンプトの作法（レビューの観点、指摘の書式など）と、結果の判定・分類。
- opencode v1 への対応。
- 割り当て表の置き場所と書式。別の壁打ちで決める（[未決](#未決)）。
- 既存のローカルスキル opencode-delegate の書き直し。このリポジトリの外の作業である。
- 変更の自動の取り消し。
- git で無視されたファイルの変更の検出。

## 却下した案

- 読み取り専用のときは kakoi を必須にする: kakoi を利用者に強制できないため。
- 読み取り専用を強制できないときは実行を断る: opencode 単体ではコマンドで読み取り専用に
  できず、スキルに強制の手段がないため。
- 読み取り専用に限定する: 用途が調査に限られるため。書き込み可にすれば使い方の幅が広がる。
- v1 と v2 の両方に対応する: フラグの分岐が本文に入り込み、v1 には `--standalone` がないため。
- opencode-delegate をそのまま移す: レビュー用のプロンプト作法と指摘の分類が混ざり、調査や
  実装に使うときにもレビューの型が出てくるため。
- 実行前に外部への送信を確認する: 名指しした時点で判断済みであるため。
- `--format json` で出力する: 判定は呼び出し元が行い、既定の形式で読めれば足りるため。
- プロンプトを `--file` で添付する: 添付ファイルとして扱われ、指示としての重みが変わるおそれが
  あるため（推測）。
- 出力ファイルを作業ディレクトリに置く: それ自体が変更一覧に入り、リポジトリも汚れるため。
- 既定の時間上限を持つ: 上限は呼び出し元の都合であり、呼び出し元が渡せば足りるため。
- git で無視されたファイルも変更一覧に入れる: 依存ディレクトリなど大量のファイルのハッシュを
  取ることになり、現実的でないため。
- README でサンドボックスの例として特定のツールを名指しする: このリポジトリと関係のない
  ツールに依存しているように読めるため。

## 人手確認チェックリスト

実際のエージェントで、opencode v2 が使える環境と、git 管理下の作業用リポジトリを使って試す。
各項目は、該当する要件の成功条件を満たすかを見る。

- C-01: `agentskills validate ./skills/ba0918-opencode-exec` が通る。本文に opencode と git 以外の
  固有のツール名や API 名、絶対パス、特定の利用者の環境の値、特定のサンドボックスの名前がない。
- C-02: opencode について質問しただけの会話で `opencode run` が起動しない。「このリポジトリの
  構成を opencode の <モデル> で調べて」と名指しすると、送信の確認なしに実行が始まる。指示
  ファイルに「調査にはこの実行役を使う」と書いた状態で調査を頼むと、同様に実行される。説明文と
  本文に、名指しのときだけ実行することと、内容が提供元に送られることが書かれている。
- C-03: モデルを渡さずに呼ぶ、存在しないプロンプトのファイルを渡す、出力の置き場所に作業
  ディレクトリの中を渡す、先頭が `-` のプロンプトを渡す。どれも実行されずに理由が返る。
- C-04: v1 の opencode をコマンド名に渡し、実行されずに v2 が必要なことと見つかった版が返る。
- C-05: 引数を表示してから本物に渡す前置きのコマンドとエージェント名を渡し、引用符と `$` を含む
  プロンプトで実行する。表示されたコマンドが [コマンド](#コマンド) の形で、プロンプトがそのままの
  文字列で届いている。結果に 5 点がそろい、出力ファイルが作業ディレクトリの外にあって実行後も
  残っている。同じ置き場所でもう一度実行し、1 回目のファイルが上書きされていない。
- C-06: 時間の上限を短く渡し、上限を過ぎたところで止まって時間切れと明記される。前置きの
  コマンドの中の opencode も止まっている。同時に動かしておいた別の opencode のプロセスは
  止まらない。
- C-07: 未コミットの変更があるファイルをさらに書き換えさせ、新しいファイルも作らせて、その両方が
  変更一覧に入る。別の回でファイルを変えてコミットまでさせ、HEAD が動いたこととそのファイルが
  入る。変更禁止を渡して書き換えさせ、結果の最初に変更が起きたことが書かれている。どの回でも
  変更は戻されていない。
- C-08: git の管理下でないディレクトリで変更禁止を渡し、結果の最初に検出できないことが書かれて
  いる。README に、v2 が必要なこととコマンド名を渡せること、内容が提供元に送られること、読み取り
  専用はスキルが強制せず呼び出し元の仕事であることが書かれ、特定のサンドボックスのツールの名前が
  ない。
- C-09: 数分かかる調査を頼み、途中で止めたり起動し直したりせずに、終了後に結果が返る。
