# ba0918-teacher 実装計画

## Goal

ユーザーが `/ba0918-teacher enable` と打つと、エージェントがコードを書く側から、ユーザーが書くのを
支える側に回る単体スキル `ba0918-teacher` が、このリポジトリの `skills/` に入り、README から
使い方が分かる状態にする。

## Specification

`docs/spec/ba0918-teacher.md`（コミット `08a6852` で承認済み）。以下、節は `#見出し名` で示す。
この計画は仕様の文章を写さない。各ステップで挙げた節を、必ず仕様書そのもので読むこと。

用語（teacher モード、学習テーマ、本質でない部分、学習記録、復習チェック）の定義は `PROJECT.md` の
Glossary 節にある。

## Approach and why

成果物はコードではなく、エージェントが読む指示文書（`SKILL.md`）である。書き方の制約は次の 4 つ
で、どれもこの計画の順番とファイル分けを決めている。

1. **本文は英語で書く。** `PROJECT.md` の「言語方針」による。仕様は日本語なので、実装は翻訳を伴う。
   仕様に出てくる日本語の言い回しは、`#文言の扱い` のとおり意図の例であって決まった文面ではない。
   `SKILL.md` には意図を英語で書き、日本語の文面をそのまま埋め込まない。エージェントが話す言語や、
   目印・記録の中に入る語の言語は、仕様どおり「使っている環境の言語（環境の設定）に従う」と書く。
   スキルの側から特定の言語を指定したり、「会話の言語」など仕様にない言い換えをしたりしない
   （`#移植性`、`#作らないもの` の「口調・人格・解説言語の指定」）。
2. **プラットフォームに依存しない書き方をする。** `PROJECT.md` の「スキル運用」と仕様の `#移植性`
   による。ツール名・モデル名・特定 CLI の呼び出し形式を書かず、「ファイルを読む」「シェルコマンドを
   実行する」のような一般的な動作で書く。
3. **セッション中ずっと要る規則を本文の先頭に置く。** Claude Code では、会話が長くなって自動要約されると、
   呼び出したスキルの本文は先頭 5,000 トークンしか残らない（公式ドキュメント
   https://code.claude.com/docs/en/skills.md の、要約後に再添付されるスキルは各スキル先頭 5,000 トークンまで
   という記述による。2026-09-11 に確認）。モードが長時間続くこのスキルでは、要約後に失われると困る
   規則ほど先頭に置く。本文の並びは次のとおりに固定する。
   - 先頭のまとまり: Step 1 の内容（呼び出し方とモードの範囲）→ Step 2 の内容（中核の規則）→
     Step 4 で書く「記録の入口」（Approach の 4 で本文に置くと決めた規則）。
     Step 2 の中では、`#目印`、`#役割`、`#段階的なヒント`、`#ユーザーのコードへの指摘`、
     `#作業を任されたとき` の規則を先に置き、`#目的`（継続の原則）、`#文言の扱い`、
     `#teacher が見てよいもの` はその後に置く。
   - 先頭のまとまりの直後に、見出し `## Other behavior` を置く。この見出しが先頭のまとまりの終わりの
     目印で、Step 6 で語数を数える境界になる。
   - `## Other behavior` の下: Step 3 の内容。
   先頭のまとまり（frontmatter から `## Other behavior` の直前まで）は、英語でおよそ 3,500 語以内に
   収める。トークン数は数えられないので、語数（`wc -w`）で代わりに測る。
4. **学習記録の書式と日付の計算は `references/record.md` に分ける。** `SKILL.md` は 500 行以内が
   `PROJECT.md` の目安で、この計画では 500 行を上限とする。記録の置き場所・書式・読めないときの条件・
   書き込めないときの扱い・日付と間隔の計算は長く、記録を読み書きするときにしか要らないので、
   別ファイルに分ける。そのうえで `SKILL.md` に「記録を読む・書く前には、毎回 `references/record.md` を
   読み直す」と書く。要約で詳細が失われても、次の読み書きの前に取り戻せるようにするためである。
   一方、作業中に記録の読み書きとは別の時点で要る規則は、`SKILL.md` の先頭のまとまりの最後に
   「記録の入口」として置く（Approach の 3）。記録の入口に置くのは次の 4 つである。
   - 記録を読む・書く前には、毎回 `references/record.md` を読むこと
   - 記録を読み書きする場面と、読み書きしない場面（仮のテーマの間、通常の作業中）
   - 作業中の「これ何だっけ？」をいつ聞くか・聞かないか（`#復習チェック` の「作業中」の箇条）
   - 概念を「理解した」にしてよい条件（`#復習チェック` の「理解した」にする条件の段落）
   ここに挙げていない記録と復習チェックの規則は、`references/record.md` と `SKILL.md` のどちらに置いてもよい
   （Left to the implementer）。

`description` には、何をするスキルかと、ユーザーが明示的に呼んだときだけ使い、自分の判断では呼ばない
ことを書く（`#コマンド`）。`PROJECT.md` は description に「発火のトリガーになる具体的キーワード」を
含めるよう定めているが、このスキルでは発火キーワードの一覧（兄弟スキル `skills/ba0918-handoff/SKILL.md`
の「日本語キーワード: …」のようなもの）を付けない。発火キーワードは LLM が自分の判断で呼ぶきっかけを
増やすもので、このスキルでは防ぎたい方向だからである（`#コマンド` の、自分の判断で呼ぶことを防ぐ要件）。

## Scope of change

- `skills/ba0918-teacher/SKILL.md`（新規）
- `skills/ba0918-teacher/references/record.md`（新規）
- `README.md`（スキル一覧と注意書きの追記のみ）

これ以外のファイルは変えない。`PROJECT.md` の Glossary と仕様書は承認済みなので触らない。
`skills/ba0918-teacher/` に `scripts/` や `assets/` は作らない（仕様の `#外部依存` はなし）。

## Step order and prerequisites

作業は `ba0918-teacher` ブランチで行う。このブランチがまだなければ、`main` の最新（仕様と計画の
コミットを含む）から作って切り替える。

1 → 2 → 3 → 4 → 5 → 6 の順に進める。

- Step 1 で骨組みとバリデータの通過を先に作る。以降のステップはすべてこの `SKILL.md` に書き足すので、
  frontmatter の誤りを最後に見つけると全部やり直しになるからである。
- Step 2 の中核の規則を Step 3 より先に書く。先頭に置く規則を先に確定させないと、後から足した節に
  押されて先頭の位置が崩れる。
- Step 4 の学習記録は、Step 2・3 の本文から参照される側なので、本文の流れが決まってから書く。
- Step 5 の README は、スキルの振る舞いが確定してから書く。
- Step 6 は全体の確認で、最後に行う。

コミットは各ステップで 1 つ作る。規則は次のとおり。

- ファイルは 1 つずつ名前を指定してステージする。`git add -A` や `git add .` は使わない。
- メッセージは日本語で、`<type>: <件名>` の形（Conventional Commits）。件名と本文には、変更の結果と
  理由を書く。「Step 2」のような計画の手順名や、作業の経緯は書かない。
- Step 6 で直すところがなければ、コミットは作らない。

## Left to the implementer

計画全体で任せること。どれを選んでも承認済みの振る舞いは変わらない。

- `SKILL.md` と `references/record.md` の中の見出し名、節の分け方、英語の言い回し。ただし本文の並びは
  Approach の 3 のとおりにし、境界の見出し `## Other behavior` はこの名前で置く。
- Approach の 4 で「記録の入口」に挙げていない記録と復習チェックの規則を、`references/record.md` と
  `SKILL.md` のどちらに置くか。どちらに置いても、仕様の規則が漏れなく書かれていればよい。
- 各規則に添える例（英語の例文やコード例）の選び方。例は意図の説明であり、決まった文面にしない。
- `description` の具体的な文面。1024 文字以内で、何をするスキルかと、ユーザーが明示的に呼んだときだけ
  使い、自分の判断では呼ばないことが書いてあればよい。

## Stop conditions

一般の 4 条件で止めて引き返す。仕様の意味が足りない・承認内容から外れる、不可逆・特権・危険な操作が
要る、影響が広がる事故が起きた、やり方を変えても進まない、の 4 つである。

このスキル特有の条件として、次の場合も止めて引き返す。

- 仕様の要件を、プラットフォーム固有の名前（ツール名、モデル名、特定 CLI の呼び出し形式）を使わずには
  英語で書けないと判断したとき。
- 仕様の日本語を英語にする過程で、2 通りに読める箇所が見つかったとき。どちらかを選んで進めない。
- `SKILL.md` が 500 行（`wc -l`、frontmatter を含む）を超え、Approach の 4 で `references/record.md` に
  置くと決めた内容を移しても収まらないとき。
- 先頭のまとまり（Approach の 3）が 3,500 語を超え、先頭に置く規則を削らないと収まらないとき。
- `agentskills validate` が、仕様が求める項目（例: frontmatter の `description`）を拒否したとき。

## Test command

このリポジトリにテストはない。検査コマンドは `PROJECT.md` の Commands 表にある
`agentskills validate ./skills/ba0918-teacher` で、これを使う。成功すると `Valid skill: ...` と表示される。

## Out of scope

- `disable-model-invocation` を `SKILL.md` に入れること（仕様の `#却下した案`）。README での案内だけ行う。
- 仕様の `#作らないもの` に挙げたもの全部。
- 学習記録ファイルそのものの作成（`~/.agents/ba0918-teacher/` はスキルが実行時に作るもので、この実装では
  作らない）。
- C-01〜C-18 の実行（受け入れのときにユーザーが行う）。
- リリース作業（バージョンやタグ）。このリポジトリにはまだその仕組みがない。

## Step 4 — 学習記録と復習チェック

Purpose: 学習記録と復習チェックの規則を書く。書式・置き場所・書き込めない／読めないときの扱い・日付と
間隔の計算は `references/record.md` に、「記録の入口」は `SKILL.md` の先頭のまとまりの最後（`## Other behavior`
の直前）に置く（Approach の 3・4）。
Specification: `#学習記録`, `#書式`, `#復習チェック`, `#保存する状態と寿命`, `#enable の流れ`（手順 2 の記録
操作、手順 3・4）, `#学習テーマの変更`, `#disable`, `#作業を任されたとき`（通常の作業中の記録の扱い）,
`#人の判断点`.
Prerequisites: Step 3。
May change: `skills/ba0918-teacher/references/record.md`（新規作成）、`skills/ba0918-teacher/SKILL.md`。
Done when: 挙げた節の規則が、どちらかのファイルに英語で書かれている。Approach の 4 で「記録の入口」に挙げた
4 つは、`SKILL.md` の `## Other behavior` の直前にある。`references/record.md` の書式は `#書式` の並びのとおりで、
見出しと欄の名前の言語についても `#書式` のとおりに書かれている。記録を読み書きする場面として、enable の
手順 2（確定後にまとめて書く）・3・4、区切り、新しい記録ファイルの作成（経験の欄を埋める）、テーマ変更、
disable が書かれている。記録を扱わない場面も書かれている。仮のテーマの間は読み書きしない。通常の作業中は
更新しない。ただし通常の作業中に disable されたときは、それまでの teacher としての部分のまとめを書く。
Step 2・3 で置いた参照がすべて中身のある記述につながっている。`#人の判断点` の表のうち、次の場面が扱われて
