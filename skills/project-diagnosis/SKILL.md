# プロジェクト診断

開発基盤が「あるか」ではなく「機能しているか」を診断し、優先順位を付けて改善する。

## このスキルの原則

1. **プロジェクトに合わせて出し分ける。** 個人のプロトタイプに mutation test を勧めない。判定の前に必ずプロファイリングを行い、項目ごとに必要度を決める。不要と判断した項目は「不要」と明示する（黙って飛ばさない）。
2. **形骸化を見つけることが本題。** 設定ファイルの存在は成果ではない。CI が常時 red、hook が回避されている、lint が warning を垂れ流している、テストが CI で実行されていない — これらは「未整備」より悪い。存在チェックで満足しない。
3. **指摘は絞る。** 全項目の一覧を並べても行動は変わらない。最も効く 3 件を主役にし、残りは付録に置く。
4. **診断で終わらない。** 承認された改善は実際に導入し、動作を確認するところまでやる。

## 手順

### 1. プロファイリング

判定基準を決めるために、まずプロジェクトの性格を掴む。ここを飛ばすと一般論のチェックリストになる。

以下を調べる。

- **種別** — ライブラリ / CLI ツール / Web アプリ・サービス / 設定・インフラ / ドキュメント / 実験・使い捨て
- **エコシステム** — 言語とパッケージマネージャ。マニフェストファイル（package.json、pyproject.toml、go.mod、Cargo.toml、Gemfile など）から判断する。モノレポなら構成も
- **規模** — コミット数、直近 1 年のコントリビュータ数、ソースファイル数
  - コントリビュータ数はコミット履歴の著者を集計して求める
- **フェーズ** — プロトタイプ（動くことが目的）/ 開発中 / 運用中（利用者がいて壊せない）
  - 判断材料: リリースタグの有無、デプロイ設定の有無、コミット頻度の継続性
- **公開性** — 公開リポジトリか、社内・個人か

この結果を最初に 3〜4 行で要約し、以降の判定の前提として提示する。

### 2. 証拠を集める

`references/checks.md` に、11 項目それぞれの「集める証拠」「形骸化のサイン」「必要度の決め方」がある。**判定を書く前にこのファイルを読む。**

対象項目:

| # | 項目 |
|---|---|
| 1 | .gitignore |
| 2 | エージェント向け指示（AGENTS.md / CLAUDE.md 等） |
| 3 | フォーマッタ |
| 4 | linter |
| 5 | 型チェック・静的解析 |
| 6 | テスト（unit / integration / e2e / mutation） |
| 7 | git hook（pre-commit / pre-push） |
| 8 | CI |
| 9 | 依存関係の健全性 |
| 10 | シークレット管理 |
| 11 | 環境の再現性 |

収集は独立しているので、並行して進めてよい。項目数が多いため、調査をサブエージェントに分割して委譲してもよい（その場合も判定は自分で行う）。

**重要**: 設定ファイルを読むだけでは形骸化は見抜けない。次を必ず併せて確認する。

- 定義されたコマンドが**実際に通るか**（少なくともフォーマッタ・linter・型チェック・テストは実行してみる。時間がかかるものは対象を絞ってよい）
- CI の直近の実行結果（成功しているか、いつから壊れているか）
- 設定ファイル同士の整合性（CI・hook・ドキュメントが同じコマンドを指しているか）

実行に失敗した場合、それ自体が最重要級の所見になる。環境未セットアップが原因なら、それは項目 11 の所見。

### 3. 判定する

各項目を 2 軸で評価する。

**必要度** — このプロジェクトにとって: 必須 / 推奨 / 任意 / 不要

**現状** — 次の 3 値で表す。

- **良好** — 導入され、機能している
- **形骸化** — 導入されているが機能していない（回避されている、壊れたまま、実行されていない、実態と乖離）
- **未整備** — 無い

優先順位は「必要度が高く、現状が悪く、直すコストが低い」順。**形骸化は未整備より優先する** — 既に投資されていて、直すコストが小さく、放置すると他の仕組みへの信頼も損なうため。

### 4. レポートする

この構成で出す。

```
## プロジェクトの性格
（プロファイリングの要約 3〜4 行）

## 今すぐ効く 3 件
1. 【項目】現状の要約
   - 根拠: 観測した事実（ファイル名・行・コマンドの出力・CI の状態）
   - 提案: 具体的に何をするか
   - コスト: 見積もり
（2, 3 も同様）

## 全項目
| 項目 | 必要度 | 現状 | 所見 |
（11 行。不要と判断した項目は必要度「不要」と理由を 1 行で）

## 導入しますか
（3 件それぞれについて、実行するか確認する）
```

守ること。

- **根拠を必ず添える。** 「テストが不足しています」ではなく「テストは 4 ファイルあるが、CI の設定にテスト実行のステップが無い（`.github/workflows/ci.yml`）」と書く。
- **一般論を書かない。** そのプロジェクトで観測した事実だけを根拠にする。
- **不要と判断した理由も書く。** これがこのスキルの価値の半分を占める。
- 良好な項目は 1 行で済ませる。

### 5. 導入する

ユーザーが承認した項目について、実際に手を動かす。`references/remediation.md` を読んでから作業する（導入時の共通原則とエコシステム別の定石が書かれている）。

進め方:

1. **1 項目ずつ。** まとめて入れない。
2. **最小構成から。** その言語で最も標準的な選択肢を、デフォルト設定で入れる。ルールのカスタマイズは後回し。
3. **既存コードの違反を初回導入と混ぜない。** 設定の追加と一括整形は別コミットに分ける。
4. **入れたら動かす。** コマンドを実行し、意図どおりに通る／落ちることを確認する。確認していないものを「導入した」と報告しない。
5. **入口を揃える。** 追加した検証は、CI・hook・ドキュメントから同じコマンド名で呼べるようにする。
6. **エージェント向け指示に反映する。** 新しいコマンドを追加したら、AGENTS.md 等の記述も更新する（存在する場合）。

## 使いどころ

- 未知のリポジトリで作業を始める前の状況把握
- 「そろそろ整備したい」が何から手を付けるか決まっていないとき
- 定期的な再診断。前回の結果が残っていれば差分を示す
