# ba0918-teacher 仕様

## 目的

LLM に実装を任せ続けて自分で書く力が落ちること、そして LLM が書いた知らない言語のコードを
レビューできないことの 2 つを、普段の実作業の中で解消する。そのために、ユーザーと LLM の
役割を逆転させるペアプログラミングのモードを、1 つの単体スキルとして提供する。

一文でいえば: `enable` から `disable` までの間、LLM はコードを書く側から、ユーザーが書くのを
支える側に回り、学んだことをユーザー個人の学習記録に残す。

対象とする悩みは次の 2 つで、どちらも同等に扱う。

- (a) 書く力の維持: 慣れた言語でも、自分で書く機会が減って書く力が落ちている
- (b) 知らない言語・分野の理解: LLM に書かせているコードを、レビューできる水準で理解したい

最優先の原則は **継続** である。ユーザーがやめてしまえば、このスキルは意味を失う。
ヒントの強さ、口出しの量、確認の頻度といった「どれだけ手伝うか」の判断が割れたときは、
ユーザーが続けられる側を選ぶ。この原則は、機密を記録に書かない、特定のプラットフォームに
依存しない、といった規則を曲げない。

### 文言の扱い

この仕様に出てくる日本語の文言（「今回は何を身につけたい？」「練習にする？普通にやる？」など）は、
すべて意図を示す例であり、決まった文面ではない。ユーザー側の言い回し（「今日はパス」
「テーマを〇〇に変えて」など）も決まった入力ではなく、teacher が意図を汲み取る。
形を固定する契約は、[目印](#目印) の `[teacher: …]` という形と、学習記録の [書式](#書式) の並び
だけである。どちらも、中に入る語は使っている環境の言語で書く。

用語（teacher モード、学習テーマ、本質でない部分、学習記録、復習チェック）の定義は
`PROJECT.md` の Glossary 節にある。

## 要件

各要件の確認方法は、末尾の [人手確認チェックリスト](#人手確認チェックリスト) の項目番号で示す。
このスキルはコードではなく指示文書なので、確認は、人が実際にエージェントで試す手順と、
公式バリデータ（`agentskills validate`）で行う。モデルを繰り返し走らせる自動測定は必須にしない。

### 移植性

スキル本文は特定のエージェントやモデルに依存しない自然言語で書く。hooks、output style、
定期実行などプラットフォーム固有の仕組みに依存しない。他のスキルにも依存しない。
口調・人格・解説の言語はスキルで定めず、使っている環境の設定に従う。スキルが定めるのは、
誰が書くか、いつ何を出すか、何を記録するか、という振る舞いだけである。

- 成功条件: `agentskills validate ./skills/ba0918-teacher` が通る。本文に固有のツール API 名、
  モデル名、特定 CLI だけで通じる呼び出し形式が現れない（人が本文を読んで確認する）。
  ユーザーの output style（例: 独自の口調設定）と併用したとき、口調はその設定のまま、
  teacher の振る舞いが働く（C-01）。
- 反例: 本文が「Skill ツールで〜」「Claude は〜」と書いている。teacher モード中だけ口調が
  スキル独自のものに変わる。

### コマンド

- `enable [学習テーマ]`: teacher モードを有効にする。学習テーマは省略できる。
- `disable`: teacher モードを終える。
- 引数なし: 現在の状態（有効か無効か、有効なら学習テーマ）と使い方を表示する。

`status` などの専用サブコマンドは作らない。想定外の呼び方は次のように扱う。

- 有効な間にテーマ付きで `enable`: [学習テーマの変更](#学習テーマの変更) として扱う。
- 有効な間にテーマなしで `enable`: 現在の状態を表示するだけにする。
- 無効なときの `disable`、または知らない引数: 引数なしと同じく、状態と使い方を表示する。

このスキルは、ユーザーが明示的に呼んだときだけ動く。LLM が自分の判断で呼ぶことを防ぐため、
次の 2 つを重ねる。

- スキルの説明文（frontmatter の `description`）に、ユーザーが明示的に呼んだときだけ使い、
  自分の判断では呼ばないことを書く。
- スキル本文に、`enable` として呼ばれても、ユーザー自身のメッセージが有効化を頼んでいなければ
  有効にせず、状態を表示するだけにすることを書く。この歯止めは `enable` にだけ働き、`disable` や
  引数なしの呼び出しには影響しない。

Claude Code 固有の frontmatter 項目 `disable-model-invocation` は SKILL.md に入れない。公式
バリデータがこの項目をエラーにし（`Unexpected fields in frontmatter`）、[移植性](#移植性) の
成功条件を満たせなくなるためである。Claude Code の利用者向けには、インストールした SKILL.md に
自分で足す方法を [README](#readme) に書く。

- 成功条件: 3 通りの呼び方と、想定外の 3 通りの呼び方が、それぞれ上記のとおり振る舞う
  （C-02, C-11, C-12, C-15）。スキルを呼ばずに「Rust を勉強したい」と話しても、teacher モードが
  有効にならない（C-18）。
- 反例: 引数なしで呼ぶと、状態を示さずに enable してしまう。有効な間に、同じ学習記録ファイルに
  対応するテーマで `enable` すると、復習チェックからやり直す。

### teacher モードの範囲

teacher モードは、そのセッションの中で `enable` してから `disable` するまで有効である。
新しいセッションには引き継がれない。新しいセッションで続けるには、もう一度 `enable` する。

- 成功条件: 新しいセッションでは目印が付かず、通常どおり LLM が実装する（C-12）。
- 反例: 前のセッションの学習記録が存在するだけで、新しいセッションで勝手に teacher として
  振る舞う。

### 目印

teacher モードが有効な間、enable 直後の応答から毎回、応答の先頭に `[teacher: <学習テーマ>]` を
付ける。目印は、指示が効いているかをユーザーがひと目で判断するための手段である。目印が消えて
いれば、モードが無効か、指示が薄れている。契約として固定するのは `[teacher: …]` という形だけで
ある。`…` の部分は次のように変わり、その語は使っている環境の言語で書く（以下は日本語の例）。

- テーマが決まる前: `テーマ未定`
- 推測したテーマで仮に進めている間: テーマの後ろに `(仮)`（例: `[teacher: 所有権(仮)]`）
- [作業を任されたとき](#作業を任されたとき) に通常の作業をしている間: `一時停止`

確認では、これらの語を文字列ではなく意味で判定する（英語の環境なら `[teacher: paused]` も
「一時停止」として合格）。

- 成功条件: enable 後のすべての応答の先頭に目印があり、テーマを変えるとその応答から目印の
  テーマも変わる。通常の作業中は一時停止を表す目印になる（C-02, C-07, C-10）。
- 反例: 解説が長い応答や、LLM が本質でない部分を代行した応答で、目印が抜ける。通常の作業中に
  目印が消え、指示が薄れたのと区別がつかない。

### enable の流れ

1. 目印を付け始める。学習テーマが引数にあればそれを使う。なければ「今回は何を身につけたい？」
   と聞き、目印は `テーマ未定` にする。
2. ユーザーがテーマに答えないまま作業を始めたら、作業内容からテーマを推測し、`(仮)` 付きの
   目印で進める。区切りのいいところで、テーマをもう一度だけ確認する。`(仮)` の間は、学習記録の
   読み書きと復習チェックを保留する。`(仮)` の間にユーザーがテーマを告げたとき（「テーマを〇〇に
   変えて」を含む）は、テーマが決まったものとして扱い、仮のテーマのファイルには触れない。
   テーマが決まったら、今の小さな作業が片付いたところで手順 3 以降を行う。決まったテーマの記録
   ファイルが仮のテーマと同じなら、`(仮)` の間に理解した概念もそのときまとめて書く。違うファイル
   になったら、`(仮)` の間に理解した概念は書かない。テーマが決まってから手順 3 を行うまでの間に
   理解した概念は、どちらの場合も決まったテーマのファイルにまとめて書く。

   テーマが決まってから手順 3 を行うまでの間（記録をまだ開いていない間）に、disable や、記録
   ファイルが変わるテーマ変更で記録へ書く必要が生じたら、書く前にその記録を開く。開くとは、
   手順 3 と同じく、ファイルがあれば読んで読めるかを確かめ、なければ名前を提案して同意を得て、
   経験を聞いてから作ることである（[学習記録](#学習記録)）。読めなければ上書きせず「読めないとき」
   に、作成や書き込みを断られたり書けなかったりしたら「書き込めないとき」に従う（どちらも
   [学習記録](#学習記録)）。開いたら、保留していた概念もあわせて書く。このように急いで開くときは、
   手順 4（復習チェックと「詰まっている」概念への言及）も、保留していた概念についての出典確認の
   促し（[解説と出典](#解説と出典)）も行わない。記録ファイルが変わるテーマ変更でこの間が終わった
   ときは、[学習テーマの変更](#学習テーマの変更) の手順で新しいファイルをその場で開き、前のテーマ
   について予定していた手順 3・4 は行わない。区切りでの書き込みは、この間も記録を開くまで
   まとめて保留する。disable の中で記録を開くやりとり（名前の提案、同意、経験の質問）の間も
   teacher モードは有効であり、終了を宣言するまで目印を付ける。
3. 学習テーマの言語・分野に対応する学習記録を読む（[学習記録](#学習記録)）。
4. 学習記録に復習時期が来た概念があれば、復習チェックを行う。「詰まっている」概念があれば
   一度だけ触れる（[復習チェック](#復習チェック)）。
5. 以降、teacher として振る舞う。

- 成功条件: テーマなしで enable すると、最初の応答がテーマ未定を表す目印で始まり、テーマを
  聞く（C-02）。答えずに作業を始めると `(仮)` 付きの目印で進み、確認はもう一度だけ来る（C-02）。
  復習時期が来た概念がある記録で enable すると、作業の前に 1〜2 問だけ復習チェックが来る
  （C-09）。テーマが決まって記録をまだ開いていない間に disable すると、記録を開いてから書く
  （C-19）。
- 反例: テーマの答えを待って作業を止める。推測したテーマを `(仮)` なしで出す。テーマの確認を
  何度も繰り返す。記録をまだ開いていない間の disable で、読めるかを確かめずに記録を上書きする。

### 役割

ユーザーがコードを打つ側（driver）、teacher が方針を示してレビューする側（navigator）に回る。
普段はユーザーが LLM に口を出して実装させているが、teacher モードではこの立場を逆にする。
題材はユーザーの実際の作業である。練習問題は、実作業に、学習テーマに合いちょうどいい難しさの
部分がないときだけ teacher が用意する。

学習テーマの外にある作業（本質でない部分。例: 文法を学ぶときの環境構築やビルド設定）は、
LLM が代行してよい。代行する前に「ここはこちらでやる」と宣言する。ユーザーが「それは自分で
やる」と言えば譲る。LLM が代行した作業の中身をユーザーが知りたそうなら解説する。

- 成功条件: 学習テーマに属する完成したコードを、ユーザーに頼まれない限り teacher が書かない。
  例外は、[段階的なヒント](#段階的なヒント) のコード片、練習問題、[レビュー練習](#レビュー練習)
  の練習用コードである。本質でない部分を代行するときは、書く前に宣言がある（C-03）。
- 反例: ユーザーが書き始める前に、teacher が「例えばこう書けます」と完成したコードを出す。
  宣言なしに設定ファイルを書き換える。

### 段階的なヒント

ユーザーが詰まったとき、または書き方や原因を聞かれたとき（「これどう書くの」「なんで
動かないの」）は、ヒントを次の順に強めていく。

1. エラーメッセージや問題のどこを読めばよいかを指す
2. 関係する概念を噛み砕いて説明する
3. 直し方の方針を言う
4. 答えのコードを見せ、なぜそうなるかを説明し直す

段階を進めるきっかけは次のどれかである。時間の経過はきっかけに使わない（LLM には見えない）。

- ユーザーが「わからない」と言った
- 同じエラーで 2 回失敗した
- 投げやりな発言が出た（例: 「もういいや」「無理」）

「同じエラー」かどうかは、メッセージの文面ではなく、原因が同じかで teacher が判断する。
失敗の回数は、teacher が自分で確かめた結果と、ユーザーが貼った出力の両方で数える
（[teacher が見てよいもの](#teacher-が見てよいもの)）。

段階は「今取り組んでいる小さな作業」（例: 「この関数を通す」）の単位で数える。同じ作業の
中で別のエラーが出ても段階は引き継ぎ、その作業が片付いたら段階 1 に戻す。書き方や原因の質問が
新しい話題についてのものなら、新しい小さな作業として段階 1 から始める。

投げやりな発言が出たときは、すぐに次の段階へ進め、さらに作業を「まずこの 1 行だけ」の
ように小さく割って提示する。

答えの一部にあたるヒントのコード片は、段階 3 以降と、投げやりな発言が出たときに、teacher の
判断で自分から出してよい。段階 1 ではコードを出さない。段階 2 では、今の作業の答えにならない
一般的な例（例: 概念だけを示す `let r = &x;`）は見せてよいが、作業の答えにつながるコード片は
出さない（投げやりな発言が出たときを除く）。答えのコード全体（段階 4）は、
ユーザーが頼んだときだけ出す。段階 3 でさらにきっかけが起きたときは、段階 3 のまま答えに
かなり近いコード片を出し、作業をさらに小さく割り、「答えを見る？」と聞く。ユーザーが応じれば
段階 4 に進む。

段階は応答に表示しない。確認する人は、応答の中身で段階を見分ける（読む場所を指していれば 1、
概念を説明していれば 2、直し方の方針を言っていれば 3、答えのコード全体なら 4）。

- 成功条件: 同じエラーで 2 回失敗すると、次の応答のヒントが 1 段階強くなる。
  「もういいや」と言うと、次の応答で段階が進み、作業が小さく割られる。段階 3 でさらに
  失敗すると、答えに近いコード片と「答えを見る？」が来て、答え全体は来ない。投げやりな発言が
  ない限り、段階 1 の応答にコードは含まれず、段階 2 の応答には答えにつながらない一般的な例しか
  含まれない（C-04）。
- 反例: 1 回目の失敗で答えのコード全体を出す。投げやりな発言に励ましだけを返し、ヒントも
  作業の分割もない。段階 3 で詰まったまま、同じ方針を繰り返すだけになる。

### teacher が見てよいもの

teacher は、作業中のファイルを自分から読んでよい。プロジェクトのビルド、テスト、チェック用の
コマンドを実行してもよい。ただし、学習テーマのコードを書き換えてはいけない（ユーザーに頼まれた
場合を除く。[作業を任されたとき](#作業を任されたとき)）。コマンドを実行できない環境では、
ユーザーに出力を貼ってもらう。teacher が実行した結果と、ユーザーが貼った同じ実行の出力は、
1 回の失敗として数える。

- 成功条件: teacher がファイルを読んだりビルドを実行したりしても、学習テーマのコードは変わらない
  （C-05）。
- 反例: 確かめるついでに学習テーマのコードを直す。

### ユーザーのコードへの指摘

- バグ、安全性の問題、コンパイルが通らない: すぐ指摘する。指摘はいつも、問題があることと、
  その場所・種類から入る（例: 「12 行目で借用のエラーが出ている」）。新しい小さな作業では、
  これが段階 1 に当たる。原因の説明から先は [段階的なヒント](#段階的なヒント) に従って進め、
  同じ小さな作業の中で段階が進んでいれば、その段階から続ける。
- 動くがその言語らしくない書き方: 動いたあとにまとめてレビューする。

どちらも、直すのはユーザーである。teacher は何がなぜ問題かを説明する。

- 成功条件: 新しい小さな作業でコンパイルが通らないコードを書くと、次の応答で問題の場所と種類が
  示され、直し方の方針や答えのコードはまだ来ない。動くが慣用的でないコードは、動いた時点でまとめて指摘される。
  どちらも teacher が修正版を書かない（C-05）。
- 反例: 書いている途中の慣用性の問題に毎回口を出して流れを止める。指摘と同時に修正版の
  コードを書く。

### 解説と出典

ユーザーに明らかに知識が足りないときは、頼まれなくても助言と解説を入れる。

言語やライブラリがどう振る舞うかの説明（文法の意味、コンパイラの規則、API の仕様など）には
出典を付ける。出典は URL、または文書名と節である。そのセッションで実際に出典を確認できたか
どうかも明記する。確認できていない説明には「LLM による説明で、未確認」と書く。
ネットワークにアクセスできない環境では、確認できないことをそのまま書く。
ユーザーのコードのロジックの説明には出典は要らない。

学習記録で概念を「理解した」にするときに、その概念の出典を開いて確かめるようユーザーに
促す。1 つの概念につき 1 回だけで、ユーザーはパスできる。詰まっている最中には促さない。

- 成功条件: 言語仕様の説明に出典と確認状況が付く（C-06）。概念を理解済みにする場面で、
  出典確認の促しが 1 回だけ来る（C-09）。
- 反例: 出典を確認していないのに、確認済みのように書く。詰まっている最中に「公式ドキュメントを
  読んでみて」とだけ返す。

### 作業を任されたとき

コードを頼まれたときは、頼まれたあともユーザーが driver のままかどうかで扱いを分ける。
書き方や原因を聞かれただけのときは、ここではなく [段階的なヒント](#段階的なヒント) で返す。

- 作業まるごとを任される（例: 「急ぎでこのバグ直して」「この機能作って」）: 「練習にする？
  普通にやる？」と、その作業について一度だけ聞く。「普通に」なら、その作業の間は通常の
  アシスタントとして振る舞い、目印は一時停止を表すもの（日本語なら `[teacher: 一時停止]`）にする。
- ユーザーが進めている作業の一部のコードを頼まれる（例: 「この関数だけ書いて」、ユーザーが
  自分で書いたコードについての「これ直して」）: 書いたうえで要点を短く説明する。自分で書くよう
  促したり引き止めたりはしない。
- どちらか判断できない: 「練習にする？普通にやる？」を聞く。

通常の作業は次のように扱う。

- 終わり: teacher が作業の完了を報告し、ユーザーが追加の依頼をしなかったとき。そこで
  teacher に戻り、目印を学習テーマに戻す。
- 途中で依頼が増えたとき: 同じ作業の続き（例: 「ついでにテストも」）ならそのまま続ける。
  別の作業なら、その作業についてもう一度「練習にする？」と聞く。
- 通常の作業中は、学習記録の更新、復習チェック、出典確認の促しを行わない。
- 通常の作業中にテーマの変更を頼まれたとき: 受け付けたことをその場で伝え、変更は通常の作業が
  終わってから反映する。
- 通常の作業中に `disable` されたとき: すぐに [disable](#disable) を行う。セッションのまとめは、
  それまでの teacher としての部分について書く。

- 成功条件: 「このバグ直して」に対して質問が 1 回だけ来る。「普通に」と答えると
  一時停止を表す目印で通常どおり実装し、完了後に目印が学習テーマに戻る。通常の作業中に
  テーマの変更を頼むと、受け付けたことが示され、作業の完了後に目印のテーマが変わる。「この関数だけ
  書いて」に対しては質問なしでコードと短い説明が来る。「これどう書くの」にはコードではなく
  段階 1 のヒントが来る（C-07）。
- 反例: 「この関数だけ書いて」に「自分で書いた方が身につくよ」と返す。「普通に」と答えた
  作業が終わっても通常モードのまま戻らない。通常の作業中に「これ何だっけ？」と聞く。

### 慣れた言語での練習

学習テーマが慣れた言語で、目的が (a) 書く力の維持のときは、ユーザーが知っていることを
長々と解説しない。段階的なヒントとコードへの指摘は、(b) のときと同じように行う。

慣れているかどうかと解説の深さは、学習記録の「経験」の欄（初めて / 読める / 普段書いている）、
記録にある概念、その場のやりとりから判断する。「経験」の欄は、学習記録のファイルを新しく作る
ときに、ユーザーに一度だけ聞いて埋める。

- 成功条件: 新しい記録ファイルを作るときに経験を一度だけ聞かれる。経験が「普段書いている」の
  言語を学習テーマにしたセッションで、基礎的な文法の解説が頼まれずに始まらない（C-08）。
- 反例: TypeScript を普段書いているユーザーに、変数宣言から説明する。enable のたびに経験を聞く。

### 学習テーマの変更

「テーマを〇〇に変えて」で、セッションの途中でもいつでも学習テーマを変えられる。
disable と enable をやり直す必要はない。

テーマが `(仮)` の間の変更は、テーマが決まったものとして [enable の流れ](#enable-の流れ) の手順 2 に従い、
以下の手順は行わない。変更によって対応する学習記録のファイルが変わるときは、次の順に行う。

1. それまでのファイルに、ここまでのセッションのまとめを 1 行書く（同じセッションでそのファイルに
   すでに行があれば、その行を書き直す。[書式](#書式)）。そのテーマで解決しなかった概念を
   「詰まっている」として書く（[復習チェック](#復習チェック)）。それまでのファイルをまだ開いて
   いなければ、書く前に [enable の流れ](#enable-の流れ) の手順 2 に従って開く。
2. 新しいテーマのファイルを読む。なければ [学習記録](#学習記録) の手順で名前を提案して作る。
3. 新しいファイルで復習時期が来た概念があれば、復習チェックを 1〜2 問行う。同じセッションで
   すでに開いたファイルに戻ってきた場合は行わない。ただし、そのファイルを [enable の流れ](#enable-の流れ)
   の手順 2 に従って急いで開いただけで、手順 4 をまだ行っていなければ、戻ってきたこのときに一度だけ
   手順 4（復習チェックと「詰まっている」概念への言及）を行う。

- 成功条件: 変更を頼んだ次の応答から目印のテーマが変わる（C-10）。Rust から TypeScript の
  テーマに変えると、Rust の記録にまとめが 1 行増え、TypeScript の記録が読まれる（C-17）。
- 反例: テーマ変更のために disable を求める。テーマを変えたのに、前の言語の記録に新しい概念を
  書き続ける。

### レビュー練習

ユーザーがコードをレビューし、teacher がそのレビューを評価する練習である。特に (b) に直結する。
teacher は、どのコードを LLM が書いたかを判定しようとしない。対象は次のどちらかである。

- ユーザーが指したコードや差分。teacher から提案するのは、ユーザーが会話で「LLM に書かせた
  コード」に触れたときだけ。
- 実作業に、学習テーマに合いちょうどいい難しさの対象がないとき、teacher が学習テーマに沿った短いコードを書き、
  問題を仕込んだ練習用のコードであることを明かしたうえで出す。

ユーザーがレビューを書いたら、teacher は見落とした問題と的外れな指摘を、出典付きで返す。

- 成功条件: ユーザーが指した差分のレビューに対し、見落とし・的外れの両方の観点で評価が
  返る（C-13）。
- 反例: ユーザーがレビューする前に、teacher が問題点を列挙してしまう。練習用コードに問題を
  仕込んだことを明かさない。

### 学習記録

ユーザーが何を身につけたかを、セッションをまたいで残す。

- 置き場所: `~/.agents/ba0918-teacher/<名前>.md`。リポジトリの外、ホームディレクトリ配下に置く。
  知識はリポジトリではなくユーザー個人に紐づくからである。
- 名前: 学習テーマの言語・分野を小文字英数字で表したもの（例: `rust`、`typescript`、`sql`）。
  言語名を含まないテーマ（例: 「エラー処理」）は、作業しているコードの言語で決める。
  2 つの分野にまたがる概念は、今の学習テーマのファイルにだけ書く。
  対応するファイルがなければ、teacher が名前を提案し、ユーザーが同意してから作る。
- 書くもの: [書式](#書式) の欄の中身だけを書く。コード例は書かない。欄の中にも、作業中の
  リポジトリのコード、社内のプロジェクト名・ホスト名、顧客名を書かない。
- 更新のタイミング: 区切りごとに少しずつ書き足す。区切りは、概念を 1 つ理解したとき、
  復習チェックをしたとき、「理解した」概念で作業中に詰まったときである。テーマが `(仮)` の間、
  テーマが決まってから記録を開くまでの間（[enable の流れ](#enable-の流れ) の手順 2）、通常の
  作業中は書かない（記録を開くまでの間の分は、開いたときにまとめて書く）。disable やテーマ変更でセッションのまとめを書くときに、
  そのセッションで解決しなかった概念を「詰まっている」として書く（[復習チェック](#復習チェック)）。
  disable のときには「次にやりたいこと」も書き換える。disable せずにセッションを閉じても、
  区切りまでの内容は残る。書き込みのたびにユーザーの許可を求める環境でも、区切りごとに書く。
- 削除しない: スキルは、概念の項目もセッションのまとめも削除・統合しない。整理はユーザーが手で行う。
- 書き込めないとき: teacher モードは続ける。記録を保存できていないことを最初に 1 回だけ
  伝え、そのセッションではそのファイルにもう書き込もうとしない。disable のときに、書き込むはず
  だったファイル全体を書式どおりに会話へ表示し、ユーザーが丸ごと貼り替えて保存できるようにする。
  ユーザーがファイルの作成や書き込みを 1 回でも断った場合も同じに扱う。止めるのはそのファイル
  だけで、ほかの記録ファイルには今までどおり書く。そのセッションで書けなかったファイルが複数
  あれば、disable のときにファイルごとに表示する。どの場合も、別の場所（リポジトリの中など）には
  書かない。
- 読めないとき: 次のどちらかに当たるファイルは読めないとみなす。どこが読めないかをユーザーに
  伝え、ファイルを上書きしない。そのセッションは「書き込めないとき」と同じに扱う。ただし
  disable のときに表示するのはファイル全体ではなく、そのセッションで足したり変えたりした項目
  だけにする（teacher は読めない部分を再現できず、全体を貼り替えるとユーザーのメモや既存の
  概念が失われるため）。ユーザーはそれを手で書き足す。
  - 必須の見出し 2（次にやりたいこと / 概念 / セッションのまとめ）のどれかがない
  - ある概念について、状態か最後に確認した日がない、「理解した」なのに次に復習する日がない、
    またはそれらの値の意味が解釈できない

  これ以外の違いは許す。ユーザーが足した行は無視してそのまま残す。見出し 2 の順番の入れ替えも
  許す。状態などの値は、意味が同じなら表記の揺れを許す（例: 「理解した」と `understood`）。

#### 書式

ユーザーが手で読み書きでき、確認のために記録を手で用意できるよう、次の並びを契約として固定する。

1. 見出し 1: 記録の名前
2. 「経験」の行: 初めて / 読める / 普段書いている のどれか（[慣れた言語での練習](#慣れた言語での練習)）
3. 見出し 2「次にやりたいこと」: 箇条書き。disable のたびに最新の内容で書き換える。
4. 見出し 2「概念」: 概念ごとに見出し 3 を 1 つ置き、その下に次の 4 行を箇条書きで持つ。
   - 状態: 理解した / 詰まっている
   - 最後に確認した日（「詰まっている」なら、詰まっていると記録した日）
   - 次に復習する日（「詰まっている」の間は空欄）
   - 出典: URL または文書名と節、および「確認済み / 未確認」（まだ出典がなければ中身は空でよい）
5. 見出し 2「セッションのまとめ」: 1 ファイルにつき 1 セッション 1 行、日付付きの箇条書きで
   書き足す。同じセッションでテーマを行き来して同じファイルに戻ったときは、新しい行を足さず、
   そのセッションの行を書き直す。

日付は `YYYY-MM-DD` で書く。見出しと欄の名前は使っている環境の言語で書く。既存のファイルが
あれば、その中の名前に合わせる。

```markdown
# rust

経験: 読める

## 次にやりたいこと
- ライフタイム注釈を自分で書けるようになる

## 概念
### 借用チェッカー
- 状態: 理解した
- 最後に確認した日: 2026-09-11
- 次に復習する日: 2026-09-12
- 出典: https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html （確認済み）

## セッションのまとめ
- 2026-09-11: 借用チェッカーのエラーの読み方を理解。ライフタイムで詰まった
```

- 成功条件: 概念を 1 つ理解した時点で、記録ファイルに書式どおりの項目が現れる（C-09）。
  ホームディレクトリに書き込めない環境、またはファイルの作成を断った場合に、未保存の通知が
  1 回だけ出て、disable 時に内容が表示される（C-14）。書式の崩れたファイルで enable すると、
  読めない箇所が示され、ファイルは変更されない（C-16）。記録にリポジトリのコードや固有名が
  含まれない（C-09 で人が確認）。
- 反例: disable 時にだけまとめて書くため、途中で閉じると何も残らない。作業中のコードを
  そのまま例として記録に貼る。書き込めないので、代わりにリポジトリの中に記録を作る。
  読めないファイルを新しい内容で上書きする。ユーザーが足したメモ行を消す。書き込みを断られた
  あとも区切りのたびに許可を求める。

### 復習チェック

人は忘れるので、学習記録の「理解した」概念を定期的に確認する。

- enable のとき: 次に復習する日が来た概念を、期限の古い順に 1〜2 個だけ出す。
- 作業中: 次に復習する日が来ている「理解した」概念が、ユーザーがこれから書くコードや話している
  コードに必要になったら、teacher が説明する前にユーザーに「これ何だっけ？」と聞く。
  1 つの概念につき 1 セッション 1 回までとし、enable のときに確認した概念はそのセッションでは
  聞かない。詰まっている最中と通常の作業中も聞かない。結果は enable 時の確認と同じように日付に
  反映する。
- 形式: 選択式にしない。「自分の言葉で説明して」か「小さいコード片を書いて」にする。
- 判定: teacher が「覚えていた / 半分 / 忘れていた」を理由とともに伝える。ユーザーは一言で
  判定を覆せる。
- 間隔: 間隔は「次に復習する日 − 最後に確認した日」の予定間隔で数える。実際に空いた日数は
  使わない。
  - 覚えていた: 予定間隔の倍にする（1 日 → 2 日 → 4 日 → …）。
  - 半分: 予定間隔を変えない。
  - 忘れていた: 間隔を 1 日に戻す。状態は「理解した」のままにする。
- パス: 「今日はパス」で飛ばせる。飛ばした概念の日付は変えず、そのセッションの間はもう聞かない
  （作業中の確認でも聞かない）。
- 同じセッションで同じ記録ファイルに戻ってきたとき（テーマの行き来）は、復習チェックをやり直さない。
  ただし、急いで開いただけで復習チェックをまだ行っていないファイルは除く（[学習テーマの変更](#学習テーマの変更) の手順 3）。

「理解した」にするのは、その概念を使ってユーザーが自分で書いたコードが動いたとき、または
ユーザーが自分の言葉で正しく説明できたときである。teacher が書いたコード（頼まれて書いたもの、
段階 4 の答え、それを貼ったもの）が動いても根拠に数えない。その場合は「今のコードが何をして
いるか、自分の言葉で説明してみて」と聞き、正しく説明できれば「理解した」にする。teacher が
判定を理由とともに伝え、ユーザーは覆せる。初めて「理解した」
にしたとき、また「詰まっている」から「理解した」にしたとき、次に復習する日は 1 日後にする。

復習チェックをしたら、最後に確認した日を今日にし、次に復習する日を「今日 ＋ 新しい間隔」にする。
例: 最後に確認した日が 2026-09-01、次に復習する日が 2026-09-03（予定間隔 2 日）の概念を
2026-09-11 に確認して覚えていれば、最後に確認した日は 2026-09-11、次に復習する日は 2026-09-15 になる。

概念を「詰まっている」にするのは、セッションのまとめを書くとき（disable かテーマ変更のとき）に、
そのセッションでまだ解決していない概念だけである。同じセッションの中で解決できた概念は、直接
「理解した」にする。すでに「理解した」概念で作業中に詰まったときは、復習で忘れていたときと
同じに扱う（状態は「理解した」のまま、間隔を 1 日に戻す）。この扱いは、そのまま解決せずに
セッションのまとめを迎えても変わらない。「詰まっている」にするのは、まだ記録にない概念か、
すでに「詰まっている」概念だけである。

「詰まっている」概念は復習チェックの対象にしない。enable のときに「前回ここで詰まっていたが、
今日やるか」と一度だけ触れ、学習テーマの候補として示す。

今日の日付は環境の情報から取る。取れなければセッションで一度だけユーザーに聞く。推測で埋めない。

- 成功条件: 復習時期が来た概念が 3 個以上ある記録で enable すると、期限の古い 1〜2 問だけが
  選択式でない形で出る。判定に応じて、最後に確認した日が今日になり、次に復習する日が今日から
  予定間隔の倍、据え置き、または 1 日後に更新される。「今日はパス」で作業に移り、日付は変わらない。「詰まっている」概念は問題にならず、
  一度だけ触れられる（C-09）。
- 反例: 復習時期の来た概念を全部出す。4 択で聞く。同じ概念を作業中に何度も聞く。日付が
  分からないのに推測で次に復習する日を書く。

### disable

1. セッションのまとめを学習記録に書き、そのセッションで解決しなかった概念を「詰まっている」と
   して書き（[復習チェック](#復習チェック) の規則に従う）、「次にやりたいこと」を書き換える。
   書き込めなかったファイルがあれば、[学習記録](#学習記録) の「書き込めないとき」「読めないとき」
   に従って会話へ表示する。テーマが `(仮)` のままなら記録は書かない。テーマは決まっているが
   記録をまだ開いていなければ、書く前に [enable の流れ](#enable-の流れ) の手順 2 に従って開く。
2. 「teacher モードを終了、ここからは通常どおり実装する」とはっきり宣言する。
3. 以降、目印を付けず、通常のアシスタントとして振る舞う。

- 成功条件: disable 後の応答に目印がない。実装を頼むと、teacher が自分でコードを書く（C-11）。
- 反例: disable 後も「自分で書いてみる？」と促し続ける。

- 成功条件: README に上記 4 点がある（人が読んで確認する）。

## 保存する状態と寿命

## 作らないもの

- 定期的に練習を促す仕組み（リマインダー・定期実行）。このスキルの責務ではない。
- ユーザーが上達したかの測定。仕様が確かめるのは teacher の振る舞いだけである。上達の判断は
  ユーザーが行い、学習記録はその材料になる。
- セッションをまたいで teacher モードを自動で有効にする仕組み。
- 口調・人格・解説言語の指定。
- コードを LLM が書いたかどうかの判定。

## 却下した案

- claude-skills リポジトリに置き、プラットフォームの仕組みを使う: 単体で持ち運べるスキルにすると決めたため。
- モードを持たず、作業ごとに呼び出す: 習慣づけには、毎回呼ばずに続けられるモードが要るため。
- 学習記録を持たず、enable のたびに知識量を聞く: 解説の深さの調整と、積み上がりが見えることが継続に効くため。
- 学習記録を sqlite にする: sqlite3 やスクリプトが必要で移植性が崩れ、数十項目なら検索機能も要らず、人が読み書きしにくいため。
- 用語集として `CONTEXT.md` を新設する: 用語集が 2 か所に分かれるため。
- 選択式の復習チェック: 思い出していなくても当たるため。
- 「これ書いて」に一度押し返す: ユーザーは折れやすいと自己申告しており、継続を優先するため。
- 時間経過でヒントを進める: LLM には時間の経過が見えないため。
- `disable-model-invocation` を SKILL.md の frontmatter 最上位に入れる: 公式バリデータが通らず、他のエージェントやバリデータが知らない項目をどう扱うかも分からないため。
- `disable-model-invocation` を frontmatter の `metadata` の下に入れる: バリデータは通るが、Claude Code がそこを読むとは考えにくく（未確認）、効果が見込めないため。
- 学習記録に teacher が考えた短いコード例を書く: 書式に置き場所がなく、ファイルが太り、仕事のコードに似た例が紛れ込む危険が増えるため。
- 詰まるたびに概念を「詰まっている」にする: 記録が詰まってばかりになり、続ける気持ちをくじくため。
- 学習記録が書けないとき、リポジトリの中など別の場所に書く: 個人の学習記録を誤ってコミットする危険があるため（記録をリポジトリの外に置く理由と同じ）。

## 人手確認チェックリスト

実際のエージェントで、実作業のあるリポジトリを使って試す。各項目は、該当する要件の成功条件を
満たすかを見る。

- C-01: 独自の output style を有効にした状態で enable し、口調が変わらず目印とヒントの振る舞いが働く。
- C-02: テーマなしで enable し、最初の応答がテーマ未定を表す目印（日本語なら `[teacher: テーマ未定]`）で始まってテーマを聞かれる。答えると目印が `[teacher: <テーマ>]` になり、以降すべての応答に付く。別のセッションでテーマなしで enable し、答えずに作業を始めると、`(仮)` 付きの目印で進み、その間は記録が読み書きされず復習チェックも来ない。テーマの確認がもう一度だけ来て、答えると今の小さな作業が片付いたところで記録が読まれる。
- C-03: 学習テーマの作業を始め、頼まない限り teacher がテーマの完成したコードを書かない。本質でない部分を代行するときは事前に宣言がある。
- C-04: 同じエラーで 2 回失敗し、ヒントが 1 段階強くなる（段階は応答の中身で見分ける）。投げやりな発言がない限り、段階 1 の応答にコードは含まれず、段階 2 の応答には答えにつながらない一般的な例しか含まれない。「もういいや」と言い、段階が進み作業が小さく割られる。段階 3 でさらに失敗し、答えに近いコード片と「答えを見る？」が来て、答え全体は来ない。応じると答えが来る。
- C-05: 新しい小さな作業で、コンパイルの通らないコードを書いて「書けた」と言い、次の応答で問題の場所と種類が示され、直し方の方針や答えのコードはまだ来ない。teacher がファイルを読んだりビルドしたりしても、学習テーマのコードは変わらない。動くが慣用的でないコードを書き、動いた後にまとめて指摘される。どちらも修正版は出ない。
- C-06: 言語仕様についての説明に、出典と確認状況が付く。
- C-07: 「このバグ直して」で練習か通常かを 1 回聞かれ、「普通に」で一時停止を表す目印のまま通常実装し、完了後に目印が学習テーマに戻る。その通常の作業中にテーマの変更を頼むと、受け付けたことが示され、完了後に目印のテーマが変わる。「この関数だけ書いて」で質問なしにコードと短い説明が来る。新しい話題について「これどう書くの」と聞き、コードではなく段階 1 のヒントが来る。
- C-08: 経験が「普段書いている」の言語をテーマにして、基礎的な解説が頼まずに始まらない。新しい記録ファイルを作るときに経験を一度だけ聞かれる。
- C-09: 概念を理解済みにした時点で、記録ファイルに書式どおりの項目が増え（次に復習する日は 1 日後、コード例なし）、出典確認の促しが 1 回来る。記録にリポジトリのコードや固有名がない。解決しないまま disable すると、その概念が「詰まっている」として記録され、最後に確認した日にその日が入り、次に復習する日は空欄になる。teacher に書いてもらったコードが動いたときは「理解した」にならず、自分の言葉での説明を求められる。書式どおりの記録に、次に復習する日を過去にした「理解した」概念を 3 個以上と「詰まっている」概念を 1 個用意して enable し、期限の古い 1〜2 問だけが選択式でない形で出て、詰まっている概念には一度だけ触れられる。判定に応じて、最後に確認した日が今日になり、次に復習する日が今日から予定間隔の倍・据え置き・1 日後に更新される。別の回で「今日はパス」と言い、作業に移って日付が変わらず、その概念はそのセッションの作業中にも聞かれない。復習日が来ている「理解した」概念が作業中に 2 回必要になっても、「これ何だっけ？」は 1 回だけ来る。enable 時に確認した概念は作業中に聞かれない。
- C-10: 「テーマを〇〇に変えて」で、次の応答から目印のテーマが変わる。
- C-11: disable で記録にまとめが書かれ、「次にやりたいこと」が書き換わり、終了宣言が出る。以降は目印がなく、実装を頼むと teacher が自分で書く。引数なしで呼ぶと、無効であることと使い方が示される。
- C-12: 新しいセッションで引数なしで呼ぶと、無効であることが示され、目印なしで通常どおり実装する。
- C-13: 差分を指してレビュー練習を行い、見落としと的外れの両方の観点で評価が返る。
- C-14: ホームディレクトリに書き込めない環境（サンドボックス等）で enable し、未保存の通知が 1 回だけ出る。以降の区切りで書き込みは試みられず、disable 時に書き込むはずだったファイル全体が書式どおりに会話に表示される。書き込みの許可を 1 回断った場合も同じになる。Rust と TypeScript の両方の記録に関わってから disable すると、ファイルごとに表示される。新しいファイルの作成を断っても、既存のほかの記録ファイルには書き込まれる。
- C-15: 有効な間に、同じ学習記録ファイルに対応するテーマ付きで enable してテーマが変わり、復習チェックはやり直されない。有効な間にテーマなしで enable して状態だけが示される。無効なときに disable し、また知らない引数で呼んで、どちらも状態と使い方が示される。
- C-16: 見出し 2「概念」を消した記録ファイルを用意して enable し、読めない箇所が示され、disable 後もファイルが変更されていない。そのセッションで概念を 1 つ理解して disable すると、表示されるのはそのセッションで足した項目だけである。別の回で、概念の下にメモ行を足し、状態を `understood` と書き、「詰まっている」概念（次に復習する日が空欄、出典が空）を含む記録で enable し、読めないとは言われず、disable 後もメモ行が残っている。
- C-17: Rust の学習テーマで作業中に TypeScript の学習テーマへ変え、Rust の記録にまとめが 1 行増え、TypeScript の記録が読まれる（なければ名前の提案と経験の質問が来る）。同じセッションで Rust に戻すと復習チェックはやり直されず、disable すると、Rust の記録のそのセッションのまとめが 1 行のまま書き直されている。
- C-18: スキルを呼ばずに「Rust を勉強したい」と話し、teacher モードが有効にならない（目印が付かない）。
- C-19: 書式どおりの記録（次に復習する日を過去にした「理解した」概念と「詰まっている」概念を含む）を用意しておく。テーマなしで enable し、答えずにその言語の作業を始めて `(仮)` で進め、テーマの再確認に答える。まだビルドが通っていない（今の小さな作業が片付いていない）うちに、ある概念を自分の言葉で説明して理解済みにしてもらい、そのまま disable する。記録が読まれてから書かれ、その概念の項目が増え、まとめが書かれる。復習チェックも「詰まっている」概念への言及も、その概念の出典確認の促しも来ない。終了宣言までの応答に目印が付いている。別の回で同じ手順を、書式を崩した記録で行い、ファイルが上書きされず読めない箇所が示される。別の回で記録ファイルがない言語で行い、名前の提案と経験の質問が来てから作られる（作成を断ると、書き込めないときと同じく disable 時に内容が表示される）。別の回で、disable の代わりに別の言語のテーマへ変え、前の言語の記録が読まれてから書かれ、新しい言語の記録がその場で開かれて復習チェックが来る。同じセッションで前の言語に戻ると、そのときに一度だけ復習チェックと「詰まっている」概念への言及が来る。
