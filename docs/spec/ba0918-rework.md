# ba0918-rework 仕様

## 目的

問題のあるコードを見つけて直す作業は、今でもレビューと改善の指示を組み合わせればできる。
このスキルは、その「見つける → 直す → 確かめる」を一回の依頼で済ませる。

一文でいえば: 人が指定した範囲を診断し、見つけた問題を、挙動が変わるものも含めて 1 件ずつ
直し、1 件ごとにテストで確かめて専用のブランチにコミットする。

ba0918-refactor とは次の点で分かれる。refactor は挙動を一切変えず、見つけたバグは報告して
終わる。このスキルは挙動を変える修正を認める。そのかわり、何が変わるかを宣言し、
変わることと変わらないことの両方をテストで確かめる。

最優先の方針は、**人への確認を増やさないこと**である。確認が多いと、人は中身を読まずに
承認するようになり、確認の意味がなくなる。LLM が実測やリポジトリの中の根拠で決められる
ことは、LLM が決めて進める。事前の確認をしないかわりに、次の 2 つを安全網にする。

- すべての修正を専用のブランチに 1 件ずつコミットする。気に入らない修正は、そのコミットを
  取り消せば戻る
- 報告に、判断の根拠と実測の結果を載せる

用語（約束の変更、聞く項目、仕様のテスト、足場のテスト）の定義は `PROJECT.md` の
Glossary 節にある。

## 成果物

1 ブランチで次を作る。

- `skills/ba0918-rework/SKILL.md`
- `skills/ba0918-rework/references/` に、観点ごとの手引き（[観点](#観点)）
- `README.md` のスキル一覧への追加
- `PROJECT.md` の Glossary への用語の追加

## 要件

各要件の確認方法は、末尾の [人手確認チェックリスト](#人手確認チェックリスト) の項目番号で示す。
このスキルはコードではなく指示文書なので、確認は、人が実際にエージェントで試す手順と、
公式バリデータ（`agentskills validate`）で行う。モデルを繰り返し走らせる自動測定は必須にしない。

### 移植性

git は作業場所とコミットの手段なので本文に書く。それ以外は、特定のエージェント、モデル、
言語、テストの仕組みに依存しない自然言語で書く。他のスキルにも依存しない（名前を挙げて
「それはこのスキルの役目ではない」と書くのはよい）。

- 成功条件: `agentskills validate ./skills/ba0918-rework` が通る。本文に git 以外の固有の
  ツール名や API 名、特定の利用者の環境の値が現れない（人が本文を読んで確認する）（C-01）。
- 反例: 「Bash ツールで pytest を実行する」と書かれている。手順の途中で ba0918-refactor を
  読み込むよう指示している。

### 動き出す条件

ファイルを変えるのは、人が範囲を指定して、直すよう頼んだときだけである。次の場合は
動かない。

- 「問題を探して」「一覧にして」のように、見つけるだけを頼まれた。これはレビューや調査の役目である
- ほかの作業の途中で、問題のあるコードに気づいた。指摘して止まる

この条件を、説明文（description）と本文の両方に書く。

- 成功条件: 説明文と本文の両方に上の条件が書かれている（人が読んで確認する）。「このファイルの
  問題を一覧にして」という依頼で、ファイルが変わらずブランチも作られない。「このディレクトリを
  rework して」という依頼で、診断から修正まで進む（C-02）。
- 反例: 一覧だけを頼まれたのに、直し始める。

### 入力

| 渡すもの | 必須か | 内容 |
|---|---|---|
| 範囲 | 必須 | ファイル、ディレクトリ、シンボル、または「直近 N コミット」（その変更されたファイルに広げる） |
| 観点の絞り込み | 任意 | [観点](#観点) のうちどれを見るか（例: セキュリティだけ）。既定はすべて |
| 事前の許可 | 任意 | 聞く項目を聞かずに進めてよいという許可（[聞く項目の扱い](#聞く項目の扱い)） |

範囲が解決できない（パスが存在しない、シンボルが見つからない）ときは、何も変えずにその理由を
返す。範囲が一度に把握しきれない大きさなら、分割を提案して止める。途中で打ち切ると、どこまで
直したかが中途半端になるためである。行数などの固定の線は引かない。診断の途中で、範囲の
ファイルを読み終える前に、読んだ内容を保てなくなると判断したら止め、そう判断した理由を分割の
提案に書く。件数の上限は設けない。

範囲が大きいとき、読むだけの診断は別のコンテキストのエージェントに任せてよい。ファイルの編集は、
呼び出されたセッションが行う。

- 成功条件: 存在しないパスを渡すと、ブランチを作らずに理由が返る（C-03）。
- 反例: 大きすぎる範囲を診断し、見つけた問題の一部だけを直して終わる。

### 観点

見る観点は次の 6 つである。

- バグ
- 設計の問題（責務の混在、依存の向きの誤りなど）
- 性能の問題（N+1 など）
- メモリリーク
- セキュリティの問題
- 仕様との矛盾

`references/` に、観点ごとの見つけ方と、直すときの落とし穴を置く（例: N+1 は、ループの中の
遅延読み込みが典型である。まとめて読み込むと、結果の順序が変わる落とし穴がある）。

仕様とは、リポジトリの中に書かれたものを指す。仕様書、README、API のドキュメント、
docstring や型に書かれた約束、テスト名である。

設計の問題は、挙動を変えない構造の変更で直すことが多い。これは refactor と違い、読みやすさの
ための小さな変形ではなく、問題を直すための構造の変更として扱う。

- 成功条件: `references/` に 6 観点それぞれの見つけ方と落とし穴がある（人が読んで確認する）（C-01）。
- 反例: 観点の手引きが SKILL.md 本文に全部書かれ、本文が 500 行を超える。

### 聞く項目の扱い

人に聞くのは、[聞く項目](../../PROJECT.md#glossary) だけである。

- (1) [約束の変更](../../PROJECT.md#glossary): I/F、UI の見た目、データ設計が変わるもの
- (2) 正しい挙動が、リポジトリの中の根拠から決められないもの

これ以外の振る舞いの変化は、根拠を示して LLM が直す。根拠になるのは、[観点](#観点) の仕様、
呼び出し元の期待、テスト、変更の履歴である。仕様とコードが食い違うときも、どちらが正しいかの
根拠がそろえば LLM が決める。根拠の出典どうしが食い違い、どちらを優先するかの根拠もないときだけ
(2) になる。コードが正しいと決まったら、
同じ項目の一部として仕様の文書も直し、報告に書く。

セキュリティの修正で入力を拒むようになる場合、その入力が仕様の上でもともと不正なもの
（インジェクションの文字列、型の範囲外の値など）なら約束の変更ではない。仕様の上で受け付けて
いた入力を拒むなら約束の変更である。

公開 API の形が変わる設計の修正と、公開 API の削除は、約束の変更である。

聞く項目は、聞く項目でない項目をすべて直した後に、一回だけまとめて聞く。各項目に、何が
変わるか、根拠、推奨を付ける。答えを得たら、続けてその場で直す。

聞く項目を土台とする項目（[直す順番](#直す順番) の依存）は、その答えを待って最後に回し、
答えが出たら土台、その上の項目の順に直す。答えが「直さない」なら、上の項目を土台を変えない形で
直せれば直し、直せなければ保留する。人が答えられない実行では、どちらも保留にし、依存の関係と
あわせて報告する。

呼び出し時に事前の許可があれば、その範囲の聞く項目は聞かずに推奨どおり進める。許可は、
約束の変更の種類（I/F、UI の見た目、データ設計）ごとか、「すべて推奨どおりでよい」の形で
受け取る。「すべて推奨どおりでよい」は、根拠から決められない項目にも及ぶ。
人が答えられない実行（無人の実行、呼び出し元がそう伝えた）では、聞く項目を直さず、
推奨付きで報告に載せる。

- 成功条件: 空のリストで落ちる関数（呼び出し元が空の結果を期待している）が、確認なしに直される。
  公開関数の引数を変える必要がある問題は、ほかの項目を直し終えた後にまとめて聞かれ、
  何が変わるか・根拠・推奨が付いている。「I/F の変更は許可」と渡すと、それが聞かれずに
  直される（C-04）。
- 反例: 内部の関数のバグを直すたびに「直してよいか」と聞く。聞く項目を見つけるたびに、
  その場で止まって聞く。

### テスト

テストは 2 種類に分ける。

- [仕様のテスト](../../PROJECT.md#glossary): 変える挙動について、「こうあるべき」を根拠から
  書く。直す前に失敗することを確かめてから直す。項目のコミットに含めて残す
- [足場のテスト](../../PROJECT.md#glossary): 変えない挙動を守るテストが無いところで、今の挙動を
  一時的に固定する。修正の最中に、宣言していない変化が起きていないかを見張るためだけに使う。
  項目のコミットに含めず、項目を終えたら消す。ただし、仕様の根拠と一致するものは仕様のテストに
  格上げし、その項目のコミットに含めて残し、報告に書く

実装に後から付けたテストは今の挙動を固定するだけで、仕様の保証にはならない。足場のテストを
残さないのはこのためである。

既存のテストの期待値を変えてよいのは、宣言した変化に当たる部分だけである。宣言した変化の外で
期待値を変える必要が出たら、意図しない変化とみなして項目を戻す（[1 件ずつ直す](#1-件ずつ直す)）。
改名や移動に伴って、テストの中の名前や import のパスを追いかけて直すのは期待値の変更ではなく、
してよい。

挙動に関わるコードの修正で、仕様のテストも足場のテストも書けない項目は、直さずに保留する。
仕様の文書だけを直す項目と、[削除](#削除) はこの対象ではない。文書の修正は食い違っていた
コードとの突き合わせを、削除は削除の節の確かめを、それぞれの確かめとし、報告に書く。

- 成功条件: 挙動を変えた項目のコミットに、その変化を表すテストが含まれ、報告に直す前の失敗の
  出力がある。報告にある足場のテストの一覧のうち、消したとされたものがどのコミットにも
  含まれていない（C-05）。
- 反例: 修正後のコードに合わせてテストを書き、それを仕様として残す。宣言外のテストの期待値を
  書き換えて通す。

### 実測が要る項目

性能とメモリリークは、結果が変わらないため、既存のテストが通るだけでは直った証拠にならない。
直す前と後を比べる（クエリの数、計測の前後、メモリ使用量の推移など）。比べるための一時的な
計測の仕組みは LLM が作ってよく、足場のテストと同じくコミットしない。作っても比べられない
項目は保留する。

UI の見た目を変えること自体は約束の変更であり、[聞く項目の扱い](#聞く項目の扱い) に従って
答えか事前の許可を得てから直す。そのうえでの確かめとして、前後のスクリーンショットを LLM が
撮って比べ、見た目の変化が宣言したものだけであることを確かめる。人には報告で見せるだけで、
この確かめのために確認は待たない。撮る手段がなければ保留する。

- 成功条件: N+1 を直した項目の報告に、前後のクエリの数がある（C-06）。
- 反例: 「まとめて読み込むようにしたので速くなったはず」とだけ書く。

### 作業場所

必ず新しいブランチ `rework/<日時>` で、HEAD から作った worktree の中で作業する。worktree は
リポジトリと同じ親ディレクトリに `<リポジトリ名>-rework-<日時>` の名前で作る。一時ディレクトリに
置かないのは、worktree を残すためである。元の作業ツリーには、作業中も終了後も一切手を触れない。
元の作業ツリーに未コミットの変更があれば、それは診断の対象外になることを報告する。
未コミットの変更があることを理由に、人に確認しない。

新しい worktree には依存パッケージやビルドの成果物がないため、プロジェクトのインストール手順を
実行する。それでも基準の全体テストを実行できなければ、何も直さずに理由を報告して止める。

ブランチ（と worktree）は、診断を終えて直す項目が 1 件以上あると分かってから、基準の全体テストの
前に作る。診断は読むだけで、ブランチを作らない。

マージも push もしない。ブランチ名と worktree の場所を報告して終わる。worktree は消さずに残す。

- 成功条件: 未コミットの変更がある状態で呼ぶと、確認なしに別の worktree で作業が進み、元の
  作業ツリーの未コミットの変更が、作業中も終了後もそのまま残っている（元の作業ツリーに一度も
  手を触れない）。終了後、元のブランチにコミットが増えていない（C-07）。
- 反例: 今のブランチに直接コミットする。元の作業ツリーでブランチを切り替えて作業する。未コミットの
  変更を stash して作業する。

### 直す順番

項目どうしに依存があれば、土台になるほうから直す。依存とは、片方の修正がもう片方の修正箇所を
書き換えることをいう。それ以外は重要度の順に直す。データ破壊とセキュリティ、バグ、仕様との
矛盾、性能とメモリ、設計の順である。データ破壊は観点ではなく、どの観点の項目にも付きうる
属性で、直さないと保存されたデータが失われるか壊れる項目を指す。
1 件直すたびに、残りの項目がまだ成り立つかを見直す。ほかの修正で消えた項目は、そのことを
報告する。

- 成功条件: 設計の修正でバグのあるコードが書き換わる組み合わせで、設計の修正が先に行われ、
  バグの項目が解消したか、新しいコードに対して直されている（C-08）。
- 反例: 先にバグを直し、その後の設計の修正でその修正を消す。

### 1 件ずつ直す

各項目を次の順で進める。

1. 何が変わるかを宣言する（変わらないなら、変わらないと宣言する）
2. 仕様のテストを書いて失敗させ、必要なら足場のテストを書く
3. 直す
4. その項目で変えたファイルを対象とするテストと、チェック（型チェック、ビルドなど）を実行する。
   対象のテストを絞れなければ全体を実行する
5. 通れば、その項目だけを 1 コミットにする。メッセージはプロジェクトの規約に従う
6. 宣言外のテストが落ちたら、その項目の変更を戻して保留し、どのテストがなぜ落ちたかを記録して
   次へ進む

作業を始める前に全体のテストを一度実行し、基準にする。その時点で失敗しているテストは記録し、
それを理由に項目を保留しない。手順 6 の「宣言外のテストが落ちた」も、基準で失敗していなかった
テストが新たに失敗したことを指す。聞く項目を直し終えた後、最後に全体をもう一度実行する。
基準で失敗していなかったテストが新たに失敗していれば、このブランチのコミットを二分探索して
壊したコミットを特定する。そのコミットと、それに依存する
後ろのコミットを、新しい順にまとめて取り消し（revert）、すべて保留にする。取り消した後に
全体をもう一度実行し、新たな失敗がなくなったことを確かめる。残っていれば、同じことを繰り返す。

- 成功条件: 各項目がそれぞれ 1 コミットになっている。宣言外のテストを壊す修正が、保留として
  報告され、ブランチの最終状態にその変更が残っていない（最後の全体テストで見つかった場合は、
  元のコミットと取り消しのコミットの両方が履歴に残る）（C-09）。
- 反例: 複数の項目を 1 コミットにまとめる。最後の全体テストの失敗を報告だけして終わる。

### 削除

使われていないコードは、到達しないことを確かめられたら削除してよい。確かめるのは、参照を
検索して見つからないこと、動的な呼び出しや設定からの参照がないこと、公開 API でないことである。
公開 API なら約束の変更として聞く項目にする。確かめきれないものは削除せず、報告する。

- 成功条件: 参照のない非公開の関数が 1 コミットで削除され、報告に確かめた内容がある（C-08）。
- 反例: 名前が文字列から組み立てられて呼ばれている関数を、検索で見つからないという理由で消す。

### 範囲の外

範囲の外に同じ問題を見つけたら、直さずに場所を報告する。直すなら、その範囲を指定して
もう一度呼んでもらう。範囲の外まで直すと、人が見る差分が予想より大きくなるためである。

範囲の中の項目でも、範囲の外の呼び出し元を直さなければ直せないものは、保留にして報告する。

ただし、仕様とコードの食い違いでコードが正しいと決まり、直すべき仕様の文書が範囲の外に
あるときは、その文書を同じ項目の一部として直す（[聞く項目の扱い](#聞く項目の扱い)）。文書を
直さないと食い違いが残り、同じ問題がまた生まれるためである。範囲の外を直してよいのはこの
場合だけである。

- 成功条件: 範囲の外にある同じ問題が、報告に場所付きで載り、直されていない。範囲の外の
  呼び出し元の変更が要る項目が保留として報告される。コードだけを範囲にした実行で、範囲の外の
  README に書かれた誤った記述が、コードが正しいと決まった項目のコミットの中で直されている（C-08）。
- 反例: 同じ問題だからと、範囲の外のファイルも直す。範囲の外の呼び出し元を書き換えて項目を直す。

### 報告

報告に次を載せる。

- 直した項目: 1 件ごとに、観点、何が変わったか、根拠、仕様のテスト、実測の前後（性能・メモリ・UI）、コミット
- 聞く項目: 聞いた内容と答え。人が答えられない実行では、推奨付きで並べる。答えで直さないと
  決まった項目は issue 案にも載せる
- 保留した項目: 理由と、直すのに何が要るか
- issue 案（タイトルと本文）: 直さなかった項目、範囲の外の同じ問題、削除を確かめきれなかった
  コード。起票は人が決める
- ほかの修正で解消した項目
- 足場のテストの一覧: 名前と、消したか格上げしたか
- ブランチ名と worktree の場所（作ったとき）
- 開始時と最後の全体テストの、コマンド、出力、成功と失敗の数

問題が見つからなかったとき、すべてが保留になったときも、正しい結果としてそのまま報告する。
ブランチを作っていなければ作らなかったこと、作っていれば空のまま残したことを書く。
報告を埋めるために、問題とまでいえない項目を足さない。

- 成功条件: どの実行の報告にも上の区分がそろい、該当なしの区分はそう書かれている（C-10）。

## 却下した案

- 名前 `ba0918-remediate`: 日本語話者になじみが薄いため。
- 名前 `ba0918-fix`: バグ修正だけに聞こえるため。
- 名前 `ba0918-overhaul`: 小さな修正には大げさなため。
- 振る舞いが変わる修正はすべて人の合意を取る: ほぼすべてのバグ修正が確認待ちになり、確認が形骸化するため。
- 仕様とコードの食い違いは毎回人に聞く: 根拠から決められる場合まで確認が増えるため。
- 診断後に直す項目を人が一回で選ぶ: 聞く必要のない項目まで確認の対象になるため。
- 後付けのテストをすべてコミットして残す: 今の挙動を固定するだけで仕様の保証にならないため。
- 未コミットの変更があるときは人に聞く: 別の worktree で作業すれば聞かずに済むため。
- 作業ツリーがきれいなときは元の作業ツリーでブランチを切り替える: 作業中に人が触ると混ざり、分岐も増えるため。
- 範囲の大きさの上限を行数で決める: 言語やファイルの密度で適切な大きさが変わり、誤判定のもとになるため。
- 直した後の UI の見た目を、人に目で確かめてもらう: LLM が前後を撮って比べられるため。
- 範囲の外の同じ問題を、合意があれば直す: 合意を取る流れ自体が確認を増やすため。
- 使われていないコードは報告だけにする（refactor と同じ）: 確かめられる場合まで人の手を煩わせるため。

## 人手確認チェックリスト

実際のエージェントで、テストのある小さな作業用リポジトリを使って試す。各項目は、該当する
要件の成功条件を満たすかを見る。

- C-01: `agentskills validate ./skills/ba0918-rework` が通る。本文に git 以外の固有のツール名や
  API 名、特定の利用者の環境の値がない。`references/` に 6 観点の見つけ方と落とし穴がある。
- C-02: 「このファイルの問題を一覧にして」でファイルが変わらずブランチも作られない。
  「このディレクトリを rework して」で診断から修正まで進む。説明文と本文に動き出す条件がある。
- C-03: 存在しないパスを渡すと、ブランチを作らずに理由が返る。問題のないファイルを渡すと、
  何も変えずにそう報告される。
- C-04: 呼び出し元が空の結果を期待しているのに空のリストで落ちる関数が、確認なしに直される。
  公開関数の引数を変える必要がある問題が、ほかを直し終えた後にまとめて聞かれ、何が変わるか・
  根拠・推奨が付いている。別の回で「I/F の変更は許可」と渡し、聞かれずに直される。
- C-05: 挙動を変えた項目のコミットに変化を表すテストがあり、報告に直す前の失敗の出力がある。
  足場のテストがどのコミットにも含まれていない。
- C-06: N+1 のあるコードで、報告に前後のクエリの数がある。
- C-07: 未コミットの変更がある状態で呼び、確認なしに別の worktree で作業が進む。元の作業ツリーの
  未コミットの変更が残り、元のブランチにコミットが増えていない。
- C-08: 設計の修正がバグのある箇所を書き換える組み合わせで、設計が先に直される。参照のない非公開の関数が削除され、
  確かめた内容が報告にある。範囲の外に置いた同じ問題が、場所付きで報告され、直されていない。
  範囲の外の呼び出し元の変更が要る項目が保留になる。コードだけを範囲にし、範囲の外の README に
  コードと食い違う誤った記述を置いた実行で、その記述が同じ項目のコミットで直されている。
- C-09: 各項目が 1 コミットになっている。宣言外のテストを壊すように仕込んだ項目が、保留として
  報告され、ブランチに残っていない。

  refactor との違いが読み取れる。
